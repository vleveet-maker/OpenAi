# Phase 10.6.1.2.2.1.1.1 Context

## Summary

This phase is the narrowest preserve-first follow-up still blocking rollout confidence.

It is not about rebuilding the Windows browser block, not about widening the public API blindly, and not about touching the 9 logged-in ChatGPT accounts beyond one named canary unless the canary path already passes.

Previous phase `10.6.1.2.2.1.1` already proved:

- direct Windows-host backup and audit succeeded
- the public HTTP edge is now active through `Caddy`
- `GET /healthz` and `GET /v1/models` work externally over HTTP
- promoted HTTP proof on canary `shared-6` passed preserve-first

The remaining gap is now only:

1. reconcile the public HTTPS/TLS path on the deployed Windows edge
2. prove one fully independent outside-client `POST /v1/chat/completions`

## Current Truth

- The deployed preserve-first Windows Server host is `192.168.88.250`.
- It already contains 9 preserved logged-in browser workers:
  - `dad`
  - `wife`
  - `shared-1`
  - `shared-2`
  - `shared-3`
  - `shared-4`
  - `shared-5`
  - `shared-6`
  - `shared-7`
- The intended safe topology is still:
  - public edge owned by Windows-side `Caddy`
  - loopback API targets `127.0.0.1:4011` for shadow and `127.0.0.1:4010` for promoted
  - `4040` and worker-agent ports remain private
- `http://77.66.186.75/healthz` now returns `200`.
- `http://77.66.186.75/v1/models` now returns `200`.
- The old external HTTP `308` redirect is gone.
- HTTPS on `https://77.66.186.75` still fails at TLS handshake.
- One fully independent outside-client `POST /v1/chat/completions` has not yet been proven through the final public edge.

## Locked Decisions

- Do not mass-restart, mass-relogin, or broadly revalidate all 9 workers for this phase.
- Keep `shared-6` as the default canary for chat proof unless direct edge truth forces a smaller canary.
- Do not expose raw `4040` or worker-agent ports as part of the public contract.
- Do not regress the already-working public HTTP path just to chase HTTPS cosmetically.
- If HTTPS activation risks the 9-account pool or the known-good HTTP edge, prefer one exact blocker verdict plus rollback over speculative changes.
- Treat the public client contract as something that must now be made explicit:
  - either `HTTPS` is made real and outside-chat proof passes
  - or one precise preserve-first blocker is recorded with the current HTTP contract kept truthful

## Phase Goal

Finish the public-edge story after the preserve-first Windows `Caddy` cutover by producing one of these truthful outcomes:

- `safe_to_promote`
- `safe_but_hold`
- `hold_preserve_accounts`

The phase is successful if the remaining uncertainty is reduced to HTTPS/TLS truth plus one independent outside-client chat proof, with no ambiguity left about what still blocks `Phase 11`.
