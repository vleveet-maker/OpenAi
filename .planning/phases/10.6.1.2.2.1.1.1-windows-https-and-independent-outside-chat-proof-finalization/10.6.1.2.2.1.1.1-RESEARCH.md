# Phase 10.6.1.2.2.1.1.1 Research

## Findings

### 1. The remaining gap is narrower than another full edge phase

The previous phase already finished the preserve-first direct host pass:

- backup and audit succeeded
- shadow canary passed
- promoted HTTP edge passed
- external HTTP `healthz` and `v1/models` now return `200`

So this follow-up should stay narrow. It does not need to revisit browser runtime, relay topology, or the canary strategy.

### 2. HTTPS/TLS is now a contract-truth problem, not an architecture problem

The next unknown is no longer whether the Windows edge can reverse proxy at all. That is already proven over HTTP.

The remaining TLS question is narrower:

- whether the intended public contract is really HTTPS on the current public identifier
- whether `Caddy` already has the right certificate/binding path and only needs a bounded correction
- or whether the blocker is a deliberate public-contract issue that must be recorded truthfully instead of hidden behind another vague edge mismatch

That means the phase must capture exact TLS truth and avoid speculative rewrites.

### 3. The independent outside chat proof should reuse the same canary discipline

The canary worker already exists: `shared-6`.

That is still the safest path because:

- it keeps the other 8 workers out of the blast radius
- it exercises the real public contract
- it converts the final unknown into one binary result:
  - independent outside chat works through the final edge
  - or one exact blocker remains

### 4. A preserve-first finish is better than a fake green verdict

Because the promoted HTTP edge is already working, the wrong move now would be to destabilize it just to force an HTTPS result.

The correct preserve-first finish is:

1. capture exact TLS truth on the deployed Windows host
2. attempt bounded HTTPS activation or reconciliation
3. prove one fully independent outside-client chat call if HTTPS or the final public contract allows it
4. end with a truthful verdict that controls whether `Phase 11` can resume

### 5. The phase must leave no ambiguity about the public client contract

After this phase, one of these must be explicit:

- `HTTPS` is the real public contract and works for `healthz`, `v1/models`, and one independent chat call
- the real public contract remains `HTTP` for now, with one exact blocker preventing HTTPS
- or preserve-first rollback is required and the project stays on hold

That explicit contract truth matters more than squeezing in one extra implementation change.

## Planning Implications

- Add dedicated requirement IDs for HTTPS/TLS truth, independent outside-client chat proof, and final unblock/hold control.
- Keep the phase canary-first and preserve-first.
- Treat HTTP success from the previous phase as already-proven baseline, not something to rediscover from scratch.
- Prefer augmenting the existing edge/probe tooling over adding a parallel mechanism.
- End with a single written verdict that directly controls `Phase 11`.

## Recommended Execution Order

1. Record exact Windows-host TLS/public-contract truth and confirm rollback point.
2. Reconcile or prove the HTTPS edge through `Caddy` without broadening the worker blast radius.
3. Run one truly independent outside-client `POST /v1/chat/completions` on canary `shared-6`.
4. Record final public-contract truth and `Phase 11` unblock/hold decision.
