## Summary

Phase 10.5.1 already removed routing noise. What remains is more focused:

- `dad` is still blocked by auth
- `wife` and `shared-1` are both blocked by the same navigation-bootstrap tail

That means the right urgent follow-up is two-part:

1. rescue the non-auth workers at the navigation/bootstrap layer
2. make dad recovery one explicit control-plane path

There is also one bounded diagnostic fallback worth preserving in the plan:

- if the current durable profiles still fail after rescue, run one temporary fresh-profile diagnostic branch without deleting the durable profiles

If one of those paths produces a fresh `stable (2/2)` worker, Phase 11 can resume. If not, the project should stay blocked with sharper evidence.

## Recommended Rescue Shape

### Pattern 1: Bounded Navigation Rescue Ladder

Make `temporary-chat-runner` try a bounded navigation rescue ladder before returning `bootstrap_navigation_failed`.

Recommended branch order:

1. reuse an already-open ChatGPT page
2. hard reload the existing ChatGPT page if one exists but looks stale
3. `goto(startUrl)` on the existing page
4. open a fresh page and `goto(startUrl)`
5. if rescue reaches auth or challenge, classify that explicitly instead of flattening it back into generic navigation failure

Every failed branch should append exact detail to `stepDetail`.

### Pattern 2: Dad Needs A Composite Renewal Flow

The simplest reliable operator path is:

```text
POST /internal/workers/:id/manual-auth/complete-and-validate
  -> stop visible auth worker
  -> start alternate_desktop
  -> run validateAlternateDesktop(workerId)
  -> return worker + validation payload
```

This removes the operator gap between "I finished login" and "did the non-visible runtime actually recover?"

### Pattern 3: Fresh Rescue Proof Only

The final decision should ignore the old one-off pass from Phase 10.5 and use only fresh proof from this phase.

Recommended proof order:

1. `wife` twice, with a controlled alternate-desktop restart between passes
2. `shared-1` with the same bounded order if `wife` still fails navigation
3. `dad` if the new auth-renewal path produces a clean validation candidate

One stable worker is enough. Full-pool parity is still out of scope.

### Pattern 4: Fresh Profile Diagnostic Branch

If durable-profile rescue still fails, the most useful next question is:

> is the runtime broken, or is the current durable profile state broken?

The safest way to answer that is not to clear current cookies in place. Instead:

1. keep the current durable profile untouched
2. start one temporary diagnostic profile on the same worker or on `shared-1`
3. do one manual visible login on that temporary profile
4. return it to alternate desktop and validate it twice if the first pass succeeds

If the fresh profile passes while the durable profile keeps failing, the project has strong evidence that the durable profile state is corrupted or poisoned. If the fresh profile also fails, the problem is more likely in runtime handoff or current ChatGPT/runtime behavior.

## Common Pitfalls

### Pitfall 1: Another Generic Navigation Failure
If the phase ends with `bootstrap_navigation_failed` again but without branch detail, the rescue did not actually increase understanding.

### Pitfall 2: Dad Recovery Without Immediate Validation
Visible auth alone is not recovery. The same phase must validate the returned non-visible runtime.

### Pitfall 3: Reusing Old Success As New Gate Evidence
The earlier `wife` success is historical evidence only. The repeatability gate in this phase must come from fresh runs.

### Pitfall 4: Destroying A Suspect Profile Before Learning From It
If a durable profile might be broken, deleting or overwriting it too early destroys evidence.
Prefer one temporary fresh-profile branch over in-place cleanup.
