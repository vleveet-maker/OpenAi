# Phase 10.5.1.1: Alternate desktop repeatability rescue - Context

**Gathered:** 2026-03-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 10.5.1 answered the current milestone question honestly:

- deterministic worker-pinned validation is real
- repeatability truth is explicit
- but no worker is actually stable

The live result at the end of 10.5.1 was:

- `wife -> bootstrap_navigation_failed @ navigation` twice in a row
- `shared-1 -> bootstrap_navigation_failed @ navigation`
- `dad -> bootstrap_auth_required @ auth_check`

That means the next urgent follow-up is not another repeatability-gate phase and not a new runtime search. It is a rescue phase whose job is:

1. give the current `alternate_desktop` runtime one bounded navigation-bootstrap recovery attempt on the non-auth workers
2. turn `dad` auth renewal into an explicit internal-admin/control-plane path instead of leaving it as a manual side quest
3. rerun repeated proof from fresh evidence and decide whether Phase 11 can finally resume

This phase covers:

1. rescue of the current `bootstrap_navigation_failed @ navigation` tail on `wife` and `shared-1`
2. explicit `dad` visible-auth renewal followed by non-visible validation
3. a fresh repeated proof and written unblock-or-stay-blocked decision

This phase does not cover:

- a brand-new browser runtime search
- public product expansion
- full parity across all three workers
- Phase 11 rollout smoke itself

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** `wife` remains the first rescue target because it is still the only worker that ever produced a proof-backed success.
- **D-02:** `shared-1` is the second rescue target because it now shares the same navigation tail as `wife`.
- **D-03:** `dad` is an auth-renewal target in this phase and may become the fallback proof candidate only after a clean renewed validation path exists.
- **D-04:** Phase 10.5's old one-off success does not count toward this phase's repeatability proof.

### Rescue Policy

- **D-05:** Rescue must stay inside the selected `alternate_desktop` runtime; do not restart runtime selection in this phase.
- **D-06:** Navigation rescue must be bounded and evidence-first. If the rescue fails, the system must say which branch failed instead of returning another opaque navigation failure.
- **D-07:** Branch-level evidence is part of the phase goal, not optional debugging garnish.
- **D-08:** A worker is only good enough for Phase 11 if it reaches `stable (2/2)` from fresh repeated proof in this phase.

### Auth Renewal Policy

- **D-09:** `dad` auth renewal must be driveable from internal admin/control-plane routes, not only by running PowerShell steps manually.
- **D-10:** Visible auth is still allowed only for manual login or reauthentication; routine use stays non-visible.
- **D-11:** If `dad` still falls back into `bootstrap_auth_required` after a clean visible renewal, keep that as architecture evidence rather than silently trusting the profile.

### Explicit Non-Goals

- **D-12:** Do not relax the repeatability gate back to "one pass is enough".
- **D-13:** Do not hide instability behind optimistic `ready` wording.
- **D-14:** Do not move to Phase 11 just because one rescue branch looks promising without repeated proof.

### the agent's Discretion

- Exact rescue branch order inside `temporary-chat-runner`
- Exact control-plane route shape for "complete login and validate"
- Exact proof order after `wife` if rescue still fails there

</decisions>

## Specific Ideas

- The same `bootstrap_navigation_failed @ navigation` tail now appears on both `wife` and `shared-1`, so the current bug shape is probably more structural than worker-specific.
- If rescue only works after reusing or reloading an existing ChatGPT page, that is acceptable for this milestone as long as it is bounded, explicit, and repeatable.
- `dad` no longer needs another vague "reauth sometime" note. It needs one explicit internal path that the operator can run and the system can verify.
- One stable worker is still enough to resume Phase 11. This phase does not need full-pool parity.

</specifics>
