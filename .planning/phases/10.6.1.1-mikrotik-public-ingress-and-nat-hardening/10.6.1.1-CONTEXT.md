# Phase 10.6.1.1: MikroTik public ingress and NAT hardening - Context

**Gathered:** 2026-03-29  
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase `10.6.1` proved three important things:

- the Linux relay server is healthy
- the real remote relay path is healthy
- the public API contract is explicit

It also isolated the remaining blocker:

- public requests to `77.66.186.75` still do not reach our deliberate `nginx` edge cleanly

Fresh manual verification after `10.6.1` narrowed this even further:

- the server itself sits on `192.168.88.2`
- the upstream router is reachable from the server at `192.168.88.1`
- `nginx` and `owmcgp-remote-relay` both work correctly on the server
- `http://127.0.0.1/healthz` and `http://127.0.0.1:8080/healthz` return `200 ok`
- `http://127.0.0.1:4010/api/relay/health` returns the expected relay auth boundary
- `http://77.66.186.75/healthz` still does not hit our edge correctly

This phase exists to stop treating that as a vague “network issue” and turn it into one explicit RouterOS/NAT/public-edge truth.

This phase covers:

1. auditing the MikroTik path that sits in front of `192.168.88.2`
2. deciding and applying one deliberate public ingress rule set for the relay
3. hardening router management exposure so the same ingress path is not also a loose admin surface
4. proving from outside that the public IP now reaches our `nginx` edge, or recording the exact remaining blocker

This phase does not cover:

- changing the relay app contract itself
- changing the worker runtime topology
- TLS automation or public product auth
- rollout smoke confidence itself; that remains `Phase 11`

</domain>

<decisions>
## Implementation Decisions

### Locked Facts

- **D-01:** The relay server itself is not the current blocker; the remaining blocker is upstream of the local `nginx` and relay processes.
- **D-02:** The server appears to live behind a MikroTik router at `192.168.88.1`, with the server itself on `192.168.88.2`.
- **D-03:** Browser/runtime work must not be mixed into this phase. The runtime baseline stays `compact visible`.
- **D-04:** Secrets, passwords, bearer tokens, and router credentials must stay out of tracked repo files and `.planning`.
- **D-05:** This phase must end with one precise verdict: public ingress is usable, or it is still blocked with an exact reason.

### Router Boundary Direction

- **D-06:** The deliberate public path should terminate on the server `nginx`, not on the raw `:4010` socket.
- **D-07:** Router management exposure and relay exposure should be treated as separate surfaces.
- **D-08:** The preferred public path is HTTP on the standard edge first; diagnostic/high ports are secondary.
- **D-09:** Any router changes should be backup-first and idempotent where possible.

### Access Reality

- **D-10:** `192.168.88.1` is reachable from the server over ICMP and TCP.
- **D-11:** RouterOS Web UI is reachable from the server, but `admin/admin` over SSH currently disconnects instead of yielding a CLI session.
- **D-12:** Execution must therefore support two branches:
  - direct router automation if CLI/API auth works
  - exact operator/sysadmin runbook if direct auth does not work

### the agent's Discretion

- Exact RouterOS access method (`ssh`, `webfig`, exported `.rsc`, or operator-assisted CLI`) as long as the phase produces explicit truth
- Exact public ingress port strategy if router/ISP policy makes standard HTTP impossible
- Exact backup/export mechanism before router changes

</decisions>

<specifics>
## Specific Ideas

- Server-local proof already says the right server processes are healthy. The next audit must capture:
  - server IP truth
  - router reachability truth
  - router management service truth
  - NAT/forwarding truth
  - WAN-vs-LAN management exposure truth
- The clean public path should be:
  - public IP -> MikroTik dst-nat -> `192.168.88.2:80` -> `nginx` -> `127.0.0.1:4010`
- Router admin surfaces such as webfig/ssh/winbox should not stay casually reachable through the same public ingress path.
- The phase should produce a simple sysadmin-facing conclusion, not only internal engineering notes.

</specifics>
