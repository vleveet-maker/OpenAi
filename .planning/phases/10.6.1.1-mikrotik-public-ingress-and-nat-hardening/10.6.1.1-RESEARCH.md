## Summary

Current evidence strongly suggests that the remaining public-API blocker lives on the router/public-edge path, not inside the application:

1. The server runs `owmcgp-remote-relay` and `nginx` correctly.
2. The relay binds `127.0.0.1:4010` by design.
3. `nginx` serves `/healthz` correctly on the server.
4. The server is on `192.168.88.2` and reaches a MikroTik router at `192.168.88.1`.
5. Public IP requests still do not reach the expected edge path.

That makes RouterOS ingress the right next boundary to harden.

## Key Findings

### Finding 1: The server is behind a router, not directly exposed

Verified from the server:

- route to `192.168.88.1` uses `eno2`
- source IP is `192.168.88.2`
- the router replies to ping

Planning implication:

- public ingress must be audited at the router
- fixing only the server app or `nginx` will not solve the outside path

### Finding 2: Local server health and public health are separate

Verified:

- `127.0.0.1/healthz` -> `200 ok`
- `127.0.0.1:8080/healthz` -> `200 ok`
- `127.0.0.1:4010/api/relay/health` -> expected relay auth behavior
- `77.66.186.75/healthz` -> not our edge

Planning implication:

- phase proof must include both server-local and outside-client checks
- success cannot be inferred from local health anymore

### Finding 3: Router management access exists, but write-path automation is uncertain

Verified:

- RouterOS web login page is reachable at `http://192.168.88.1`
- ports `80`, `8291`, and `22` respond from the server
- `admin/admin` over SSH disconnects instead of opening a CLI session

Planning implication:

- execution must support a bounded “audit-only until auth works” path
- a successful phase can still end partial if router auth or ISP edge blocks changes, as long as the blocker is precise

### Finding 4: The safest ingress target is the server nginx edge

Because the relay process intentionally binds only to localhost now, the correct public target is not the raw Node port. The right path is:

- public IP -> RouterOS NAT -> server `:80` -> `nginx` -> `127.0.0.1:4010`

Planning implication:

- NAT and filter changes should target the server `nginx` edge
- router management services should be constrained separately

## Recommended Direction

### Wave 1

Create one repeatable router/server audit path that records:

- server LAN IP
- router reachability
- RouterOS service exposure
- current NAT/filter state
- current public-IP symptom

### Wave 2

Add or document one deliberate NAT path to `192.168.88.2:80` and harden router admin services away from WAN exposure.

Official RouterOS guidance supports this direction:

- `dst-nat` is the normal mechanism for forwarding inbound WAN traffic to a private LAN host.
- `/ip service` supports address scoping so router management services can stay limited to LAN ranges instead of sharing the public edge.
- connection tracking can preserve old flow behavior after NAT changes, so proof should use fresh requests and may require clearing stale connection state during execution.

### Wave 3

Prove from outside that:

- `http://77.66.186.75/healthz` reaches our `nginx`
- `http://77.66.186.75/api/relay/health` reaches our relay edge

If this still fails, the phase should end with a precise blocker such as:

- RouterOS auth unavailable
- NAT rule conflict
- upstream ISP/provider edge interception
