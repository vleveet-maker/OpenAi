## Summary

The codebase already contains the beginnings of compact visible runtime, but it is still half-promoted and half-incidental:

- `start-host-native-worker.ps1` already knows how to place compact corner windows and marks them as `host_visible_compact`
- internal admin already exposes `Use compact visible runtime`
- recent live work proved real relay on several compact-visible profiles
- popup hardening logic now exists in the launcher and stop script

The remaining planning problem is not "invent compact visible". It is "formalize and align the control-plane around it".

That alignment likely needs three moves:

1. make compact visible a first-class runtime path instead of piggybacking on `visible_auth`
2. roll the official worker inventory forward so the control-plane and scripts agree on the current household pool
3. treat popup hardening and compact-visible proof as milestone artifacts, not ad-hoc fixes

## What The Code Already Proves

### Pattern 1: Compact Visible Already Exists As A Runtime Class

`start-host-native-worker.ps1` already sets:

- `WORKER_RUNTIME_CLASS=host_visible_compact`
- `WORKER_RUNTIME_MODE=visible_auth`
- `WORKER_BROWSER_WINDOW_MODE=CompactCorner`

That means the system already distinguishes compact visible at the runtime-class level, but not yet at the runtime-mode vocabulary level.

Planning implication:

- the phase should decide whether to keep compact visible as `visible_auth + CompactCorner`
- or promote it to an explicit control-plane runtime concept everywhere it matters

### Pattern 2: Popup Hardening Is Real But Fragmented

Current popup-hardening logic already exists in the launch/stop scripts:

- graceful close before force-kill
- cleanup of `Local State`, `Preferences`, `Last Session`, `Last Tabs`, `Current Session`, `Current Tabs`, and `Default/Sessions/*`
- startup flags such as `--hide-crash-restore-bubble`, `--disable-session-crashed-bubble`, `--no-first-run`, `--no-default-browser-check`

Planning implication:

- popup hardening should become a named deliverable with regression coverage
- the phase should verify that only crash/session-restore artifacts are touched, not durable auth state

### Pattern 3: The Official Worker Inventory Is Behind Reality

Control-plane defaults still only know about:

- `dad`
- `wife`
- `shared-1`

But compact-corner slot logic already knows about:

- `shared-2`
- `shared-3`
- `shared-4`

and recent live work used those extra profiles successfully.

Planning implication:

- either promote `shared-2/3/4` into official host-controller + control-api + pool scripts now
- or keep them diagnostic-only and say so explicitly

### Pattern 4: Phase 11 Still Needs Proof, Not Just Runtime Flags

The milestone gate still expects proof, not only start/health success. The proof path remains:

- real ChatGPT page
- `Temporary Chat`
- preferred model selection (`GPT-5.4 Thinking`)
- real relay response

Planning implication:

- the final wave should end with a worker-by-worker compact-visible verification artifact
- that artifact should drive the new unblock/stay-blocked decision for `Phase 11`

## Recommended Planning Shape

### Pattern 1: Runtime Formalization First

Do not start with proof scripts. First make compact visible an intentional runtime path in:

- host-controller config and startup behavior
- control-api worker/runtime vocabulary
- internal admin copy and action semantics
- worker truth / status reporting

Otherwise proof can pass while the operator surface still describes the wrong baseline runtime.

### Pattern 2: Roll Out The Real Worker Set Deliberately

The phase should explicitly choose one of two paths:

1. promote `shared-2`, `shared-3`, `shared-4` into the official pool now
2. leave them outside the official pool and document that compact-visible proof currently relies on a smaller formal set

The first path seems more aligned with recent live work, but it will require:

- new per-worker start wrappers
- updated host-controller config
- updated compose/control-api worker definitions
- updated pool scripts and tests

### Pattern 3: Popup Hardening Needs Direct Regression Coverage

Popup handling should not remain only as PowerShell behavior. It needs explicit regression assertions around:

- graceful stop before force kill
- cleanup of crash/restore artifacts only
- presence of crash-bubble suppression flags in compact-visible launches

The most important truth to preserve:

> suppress the popup without erasing durable login state

### Pattern 4: End With A Worker-by-Worker Capability Snapshot

The last plan should not stop at "one compact-visible smoke passed". It should produce:

- named workers tested
- runtime class used
- bootstrap result
- relay result
- whether the worker counts as rollout-usable for `Phase 11`

That gives Phase 11 a real baseline instead of another fuzzy runtime story.

## Common Pitfalls

### Pitfall 1: Treating Compact Visible As Purely A UI Detail
It is not just a small window size. It changes runtime expectations, operator behavior, and rollout evidence.

### Pitfall 2: Suppressing The Popup By Nuking Profiles
Deleting or recreating durable profiles would hide the bug but destroy the household login state we actually want to keep.

### Pitfall 3: Promoting Extra Workers Without Updating The Whole Stack
If `shared-2/3/4` are added only in one config or only in one script, the pool will drift again.

### Pitfall 4: Calling Compact Visible "repeatable" From One Lucky Run
The phase still needs written worker-by-worker proof or a clear blocked decision.
