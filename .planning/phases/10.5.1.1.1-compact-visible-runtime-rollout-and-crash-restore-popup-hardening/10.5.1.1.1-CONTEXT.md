# Phase 10.5.1.1.1: Compact visible runtime rollout and crash-restore popup hardening - Context

**Gathered:** 2026-03-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 10.5.1.1 ended with a clear answer:

- visible ChatGPT auth still works on real profiles
- alternate-desktop hand-off is still the weak point
- compact visible runtime now looks like the practical fallback for `v1.2`

Recent live work shifted the runtime question again:

1. compact visible runs in small corner windows instead of large intrusive windows
2. real relay succeeded on multiple profiles in this mode
3. Edge `Restore pages` popup became a first-class stability hazard and now needs explicit hardening
4. current control-plane still treats only `dad`, `wife`, and `shared-1` as the official host pool, even though `shared-2`, `shared-3`, and `shared-4` were also opened, authenticated, and smoke-tested manually

This phase exists to formalize that new reality.

This phase covers:

1. treating compact visible as an intentional runtime path instead of an ad-hoc emergency fallback
2. hardening browser start and stop so crash-restore popups do not poison bootstrap or relay runs
3. deciding whether the official compact-visible pool should remain the current three workers or expand to the six authenticated host profiles
4. ending with written runtime proof that compact visible either gives `Phase 11` a real baseline or still needs another rescue

This phase does not cover:

- returning to hidden runtime or alternate-desktop experimentation
- a new browser runtime search
- mobile product UX expansion
- billing, entitlements, or public rollout work
- Phase 11 rollout smoke itself

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** Compact visible is now the leading practical fallback runtime for `v1.2`, ahead of alternate desktop.
- **D-02:** Windows may be visible only when explicitly needed, and they must stay compact and corner-positioned rather than normal full-size windows.
- **D-03:** All browser windows should be closed again after proof work; do not leave the desktop cluttered after validation.
- **D-04:** Edge `Restore pages` popup is a real runtime hazard, not cosmetic noise, because it can hide the actual ChatGPT surface and confuse proof results.

### Runtime Policy

- **D-05:** This phase must not reopen runtime selection; it formalizes compact visible and proves or rejects it as the current rollout path.
- **D-06:** Compact visible uses the existing visible Chromium session and durable profile; it is not a separate authentication model.
- **D-07:** Startup and shutdown hardening must preserve durable login state while removing only crash/session-restore artifacts that trigger the popup.
- **D-08:** Control-plane truth must say when a worker is `host_visible_compact` and must not pretend that alternate desktop is still the likely baseline.

### Pool Rollout Policy

- **D-09:** The plan must explicitly decide whether `shared-2`, `shared-3`, and `shared-4` join the official host-controller/control-api pool now or remain diagnostic-only for this milestone.
- **D-10:** If the extra workers are promoted into the official pool, the worker inventory, scripts, tests, and operator surface must all agree on the same set.
- **D-11:** If the extra workers are not promoted yet, the phase must still record why and what evidence is missing.

### Proof Policy

- **D-12:** Proof still means real `Temporary Chat -> GPT-5.4 Thinking -> relay response`, not only health or bootstrap.
- **D-13:** The phase should end with worker-by-worker truth for the official compact-visible pool, not only one lucky run.
- **D-14:** One successful worker may be enough to unblock `Phase 11`, but the artifact must say whether the wider pool is stable, provisional, or still partial.

### Explicit Non-Goals

- **D-15:** Do not wipe durable profiles just to silence the popup.
- **D-16:** Do not silently accept big normal windows as the new routine mode.
- **D-17:** Do not keep alternate desktop as the implied baseline if compact visible now has better live evidence.

### the agent's Discretion

- Exact requirement wording for promoting `shared-2/3/4`
- Exact split between runtime-foundation work and proof/reporting work
- Exact repeatability threshold for the compact-visible unblock decision if the current `stable (2/2)` rule needs worker-by-worker interpretation

</decisions>

<specifics>
## Specific Ideas

- `shared-2`, `shared-3`, and `shared-4` already have durable host-profile directories and were used for manual authenticated smoke work, but they are not yet part of the official host-controller config.
- Compact-corner placement logic already knows about slots for `dad`, `wife`, `shared-1`, `shared-2`, `shared-3`, and `shared-4`, which suggests the runtime shape is already drifting toward a six-worker layout.
- Popup hardening should prefer graceful browser shutdown first, then targeted cleanup of restore artifacts, then hidden startup flags. This is better than deleting login state or pretending the popup is harmless.
- The likely phase split is:
  1. runtime/pool formalization
  2. popup hardening and regression coverage
  3. compact-visible proof plus explicit `Phase 11` decision

</specifics>
