# Phase 05.1: Internal Browser Access for Manual ChatGPT Login and Reauthentication - Research

**Completed:** 2026-03-28  
**Question answered:** What is the smallest safe way to give the household operator live browser access to a worker for manual ChatGPT login or reauthentication inside the current Docker stack?

## Findings

### Current Codebase Reality

- `control-api` already has internal worker routes, logical reauth sessions, and an internal admin page, but there is no route that opens a visible worker browser.
- The worker runtime now boots successfully in Docker using the official Playwright image plus `xvfb-run`, and `/health` can stay up even if the initial `chatgpt.com` navigation is slow or challenged.
- The current internal edge on `127.0.0.1:8081` is already the right trust boundary for operator-only access. The missing piece is a browser viewer path routed through that same boundary.

### Source-Backed Constraints

- Playwright's official Docker guidance says headed browser execution on Linux requires `Xvfb`, and their Docker image has `Xvfb` pre-installed. That matches the worker runtime we already validated in Docker. Source: Playwright CI docs, headed mode under Docker.
- noVNC's official README describes noVNC as a browser-based VNC client that works in modern browsers and expects a VNC server plus a WebSocket proxy such as `websockify`. Source: noVNC README.
- websockify's official README describes it as a WebSocket-to-TCP bridge and documents running it in Docker, which fits an internal worker-side bridge from browser WebSockets to container-local VNC. Source: websockify README.
- Nginx's official `auth_request` documentation allows a proxy location to ask an authorization endpoint for a `2xx`/`403` decision before forwarding the request. That is a strong fit for protecting worker browser viewer traffic with short-lived access sessions from `control-api`. Source: `ngx_http_auth_request_module` docs.

### Alternatives Considered

#### 1. noVNC + websockify + VNC inside each worker container

- Best fit for the current stack.
- Keeps operator access in the browser, so the existing internal admin page can launch it directly.
- Stays inside the Docker network and existing internal edge.
- Works well with the already validated headed Chromium + X display model.

#### 2. Raw Chrome DevTools remote debugging

- Rejected for v1 operator UX.
- It would require a second browser or DevTools-specific workflow, is harder to secure cleanly through the existing edge, and is a worse fit for "open browser, log in manually" than a normal visible desktop view.

#### 3. Host-level GUI, RDP, or Docker Desktop manual inspection

- Rejected as the primary product path.
- It breaks the internal-admin contract, depends on local workstation setup, and does not produce a stable operator workflow inside the app stack.

## Recommended Direction

- Keep the official Playwright worker image lineage, but move workers to a custom runtime image that adds:
  - a persistent X display instead of `xvfb-run` wrapping the command
  - a lightweight window manager
  - `x11vnc`
  - `websockify`
  - noVNC static assets
- Expose noVNC only on the private Docker worker network, not on host ports.
- Add browser access sessions in `control-api` with:
  - `workerId`
  - `mode` exactly `first_login` or `reauth`
  - random `sessionId`
  - random `accessToken`
  - `startedAt`
  - `expiresAt`
  - status lifecycle `requested`, `browser_ready`, `waiting_for_operator`, `completed`, `expired`, `cancelled`
- Keep browser viewer traffic behind the internal edge:
  - public `:8080` returns `404` for `/internal/browser/*`
  - internal `:8081` proxies `/internal/browser/<workerId>/*`
  - Nginx uses `auth_request` to ask `control-api` whether the current worker/token/session is authorized before proxying
- Extend the internal admin page so the operator can:
  - start browser access
  - open the browser viewer in a new tab
  - cancel access
  - complete login/reauth and return the worker to `ready`

## Validation Architecture

- Automated verification should cover:
  - worker runtime metadata for browser access readiness
  - control-api browser access session lifecycle and authorization endpoint behavior
  - internal-edge contract for protected `/internal/browser/*` proxying and public `404` blocking
  - internal admin page controls and endpoint wiring
- Manual verification is still required for the real ChatGPT flow because a human must complete login or challenge steps in the live browser.
