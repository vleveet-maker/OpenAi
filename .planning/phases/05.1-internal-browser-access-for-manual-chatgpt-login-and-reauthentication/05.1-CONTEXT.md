# Phase 05.1: Internal Browser Access for Manual ChatGPT Login and Reauthentication - Context

**Gathered:** 2026-03-28
**Status:** Ready for planning

## Phase Boundary

Phase 05.1 closes the gap between the current logical reauthentication flow and a real operator-visible browser access path. The stack now boots `edge`, `control-api`, `session-client`, and all three Playwright workers successfully in Docker, and the internal/public boundary has been smoke-tested live. What still does not exist is the operator-facing path that lets a human open a live worker browser, complete ChatGPT login or challenge steps manually, and then return the worker to `ready`.

This phase is not about end-user browser access, automated login, or a richer product surface. It exists to make the already-chosen manual-auth model actually usable in the running system.

## Locked Decisions

- Manual ChatGPT login and reauthentication remain operator-only workflows. The system must not store plaintext usernames, passwords, or reusable login secrets.
- Browser access must stay internal-only behind the existing admin entrypoint on `127.0.0.1:8081`.
- End users must never reach raw worker browser controls, noVNC endpoints, VNC ports, DevTools ports, or recovery tools from the public app.
- Worker browser profiles continue living in the existing durable mounts under `/srv/chatgpt-workers/profiles/<worker-id>`.
- The current Docker worker topology and Playwright worker baseline stay in place. This phase extends the worker runtime instead of replacing it with a new orchestration product.
- The operator path must be worker-scoped and time-bounded so access is explicit, reviewable, and easy to expire or cancel.

## Specific Ideas

- The current `POST /internal/workers/:id/reauth/start` route creates only a logical recovery session. It does not provide a usable browser window.
- The live Docker smoke test proved the worker runtime can now boot headed Chromium inside Docker using the official Playwright image and `Xvfb`.
- The missing capability is therefore not browser launch itself. It is secure operator access to that running browser.
- The implementation mechanism is still open for planning, but it must fit the existing admin surface and internal edge rather than requiring direct Docker Desktop interaction.

## Deferred Ideas

- End-user remote desktop or raw browser access
- Automated login, CAPTCHA solving, or unattended reauthentication
- Public auth, billing, or tenant-aware access control
- A fully redesigned admin product separate from `control-api`
