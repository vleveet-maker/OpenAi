# Phase 10.6.1.2.2.1.1 Validation

## Validation Focus

This phase is valid only if it turns the current repo-side preserve-first toolkit into a real deployed-host result without risking the 9 live accounts.

It is invalid if it:

- mass-starts or mass-restarts the 9 workers just to test the edge
- rewrites `Caddy` blindly without a verified backup and rollback point
- declares success based only on local loopback proof without outside-client proof
- opens `4040` or worker-agent ports as part of the public contract
- ends with another vague `Caddy mismatch` instead of a narrow verdict

## Required Evidence

- one direct Windows-host audit artifact after running the backup/audit helpers on the deployed server
- one explicit backup path for the current `Caddy` config/state
- one shadow canary proof on `shared-6`
- one promoted-edge proof or one explicit rollback record
- one outside-client proof against `77.66.186.75`
- one final verification artifact with verdict

## What Must Be True Before Closeout

- the exact owner of `80`, `443`, `4010`, and `4040` on the deployed Windows host is recorded truthfully
- `shared-6` is the only required worker for the canary proof unless the direct host audit justifies a smaller canary
- shadow path is proven before promoted cutover
- promoted path is either proven or rolled back explicitly
- outside-client proof is attempted against the real public IP
- the final verdict is exactly one of:
  - `safe_to_promote`
  - `safe_but_hold`
  - `hold_preserve_accounts`

## Recommended Checks

- run `backup-public-edge-state.ps1` on the deployed Windows host
- run `collect-public-edge-audit.ps1` on the deployed Windows host
- start shadow API on `127.0.0.1:4011` and prove local canary `shared-6`
- activate shadow edge and prove through the actual `Caddy` path
- start promoted API on `127.0.0.1:4010` and prove through `Caddy`
- rollback immediately if promoted proof fails
- verify from outside `77.66.186.75`
