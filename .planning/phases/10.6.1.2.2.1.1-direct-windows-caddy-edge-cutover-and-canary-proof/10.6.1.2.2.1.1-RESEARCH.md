# Phase 10.6.1.2.2.1.1 Research

## Findings

### 1. The next gap is execution, not more edge design

Previous phases already proved the design intent:

- the Windows-side API should stay on loopback
- `Caddy` should own `80/443`
- shadow should point to `127.0.0.1:4011`
- promoted should point to `127.0.0.1:4010`
- preserve-first means canary before any broad change

So this follow-up should not spend effort on inventing another edge architecture. It should make one direct deployed-host pass through the edge that already exists.

### 2. Direct Windows-host truth matters more than inferred truth now

Outside proof and Linux pivot proof were enough to narrow the blocker, but not enough to close it:

- outside clients see `308`
- the Windows host shows `80/443` open, `4010` closed
- repo-side scripts exist but were not executed on the host yet

At this point, the missing truth is:

- the exact active `Caddy` service/config on the Windows host
- whether the host's current `308` path is one config tweak away from a working reverse proxy
- whether `https` failure is just a missing local cert/TLS config detail or evidence of a broader edge mismatch

That means the next phase should center on one direct Windows admin pass rather than more remote inference.

### 3. `Caddy` still fits the safest preserve-first topology

Official `Caddy` docs still support the same safe shape:

- `reverse_proxy` to loopback upstreams like `127.0.0.1:4011` or `127.0.0.1:4010`
- `validate` before reload
- `reload` for zero-downtime config update

That keeps:

- public edge on `80/443`
- API internals on loopback
- rollback small and local

For a host already holding 9 live ChatGPT accounts, this is safer than opening more raw ports or replacing the edge process.

### 4. The direct host pass should be canary-first and script-led

The safest sequence is:

1. run backup and audit scripts on the deployed Windows host
2. start shadow API on `127.0.0.1:4011`
3. activate `Caddy` shadow config
4. prove `healthz`, `v1/models`, and `v1/chat/completions` on canary `shared-6`
5. only then run promoted API on `127.0.0.1:4010`
6. switch `Caddy` to promoted config
7. prove outside-client path
8. roll back immediately if promoted proof fails

This keeps the remaining 8 profiles out of the blast radius.

### 5. The phase must end with a verdict, not just raw proof

The likely outcomes are now narrow:

- `safe_to_promote`: promoted path works and outside proof passes
- `safe_but_hold`: direct host path mostly works, but one bounded issue means broad use should still wait
- `hold_preserve_accounts`: promoted path still cannot be proven safely and rollback is the right preserve-first move

That verdict should explicitly control whether `Phase 11` can resume.

## Planning Implications

- Add new requirement IDs specifically about direct host backup/audit, shadow canary, promoted cutover, and outside proof.
- Treat repo-side script adjustment as optional support work, not the main goal.
- Make the direct deployed-host execution artifact first-class.
- Keep `shared-6` as the named canary and keep the 8 remaining workers untouched unless the canary path passes.
- End with one explicit verdict and a `Phase 11` unblock/hold statement.

## Recommended Execution Order

1. Direct Windows-host backup and audit with exact `Caddy` ownership truth.
2. Shadow canary on `shared-6` through `Caddy -> 127.0.0.1:4011`.
3. Promoted path through `Caddy -> 127.0.0.1:4010` or immediate rollback.
4. Outside-client proof on `77.66.186.75`.
5. Final verdict and `Phase 11` unblock/hold decision.
