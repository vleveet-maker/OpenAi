# Phase 10.6.1.2.2.1.1 Context

## Summary

This phase is not about rebuilding the Windows browser block, not about re-logging the 9 accounts, and not about inventing another API shape.

The repo-side prep now exists already:

- preserve-first backup and audit helpers exist
- shadow and promoted edge scripts exist
- Windows-side API docs and canary flow exist
- outside proof already narrowed the blocker to the deployed Windows edge itself

So the remaining work is one direct Windows-host execution pass:

1. back up and audit the real `Caddy` edge on the deployed Windows Server
2. prove the shadow path on allowlisted canary `shared-6`
3. either prove the promoted edge or roll it back cleanly
4. end with a truthful outside-client verdict

## Locked Decisions

- Do not delete, reset, overwrite, or mass-relogin the 9 deployed browser profiles.
- Do not expose `4040` or worker-agent ports as the public API boundary.
- Do not treat raw public `:4010` as the intended client contract.
- Use direct Windows-host admin execution for this phase; do not keep inferring the edge only from Linux pivots or outside redirects.
- Use staged cutover:
  1. backup and audit
  2. shadow path on `127.0.0.1:4011`
  3. canary `shared-6`
  4. promoted path on `127.0.0.1:4010`
  5. rollback immediately if promoted proof fails
- If direct Windows-host truth differs from repo assumptions, adapt the scripts and docs to that truth instead of forcing the host into the assumed shape.

## Phase Goal

Execute one preserve-first direct Windows-host `Caddy` cutover and canary proof on the deployed server, then end with either:

- `safe_to_promote`
- `safe_but_hold`
- `hold_preserve_accounts`
