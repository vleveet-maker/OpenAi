## Summary

Phase 10.6 already proved the hard part of orchestration:

1. Linux remote relay service exists and starts automatically.
2. The browser runtime can still live on a separate Windows host.
3. A real remote `ask` succeeded.

What is missing now is not "does the relay work at all," but "how do we verify it routinely and how do outside clients use it safely."

## Key Findings

### Finding 1: Raw relay port is not a stable public contract

`owmcgp-remote-relay` currently listens on `0.0.0.0:4010`, but that socket is not yet a trustworthy public consumer path:

- localhost calls on the server work
- direct calls to `77.66.186.75:4010` were not clean during verification
- this means process health and public ingress health are different truths

Planning implication:

- add a deliberate ingress path in front of the relay
- keep raw service health and public edge health as separate checks

### Finding 2: One successful worker is not enough for outside use

Phase 10.6 proved `wife` through the real remote topology. That is necessary, but not enough for a public-ready service. The service boundary must know whether each official worker is:

- usable
- auth_required
- bootstrap_failed
- relay_failed

Planning implication:

- perform a worker-by-worker audit through the remote relay path
- write a machine-readable or at least explicit matrix artifact

### Finding 3: Reverse-tunneled separate-host runtime is already a valid topology

The project no longer needs to argue whether the remote relay can work without moving the browser runtime to Linux. That is already proven.

Planning implication:

- public API readiness can proceed without waiting for a Linux browser-runtime replacement
- docs must state that the relay is remote but the runtime remains separate-host

### Finding 4: Outside clients need one stable front door

Other clients should not depend on:

- localhost-only checks
- raw port assumptions
- internal admin routes
- SSH knowledge

Planning implication:

- the next boundary should be one documented public path, ideally via `nginx` or equivalent reverse proxy in front of the relay
- relay should stay the app process, edge should stay the public-facing boundary

## Recommended Direction

### Server Verification

Add one operator verification path that checks:

- service enabled/active
- local relay `health`
- edge ingress `health`
- current topology hint
- restart/status/journal commands

### Worker and Session Verification

Add one worker-pinned remote smoke flow for all six official workers:

- start worker only when needed
- route remote proof intentionally into that worker
- classify result
- stop worker again when finished

### Public API Readiness

Use a deliberate reverse proxy or equivalent edge:

- keep raw relay behind the edge
- expose only the intended public relay routes
- document auth, request examples, error examples, and current runtime topology
