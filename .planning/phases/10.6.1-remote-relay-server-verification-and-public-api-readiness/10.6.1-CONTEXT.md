# Phase 10.6.1: Remote relay server verification and public API readiness - Context

**Gathered:** 2026-03-29  
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 10.6 proved something important and narrow:

- the relay/session/bootstrap module really runs on `77.66.186.75`
- `systemd` autostart is real
- the remote API really answered through a reverse-tunneled `wife` worker

But three truths are still not explicit enough for routine or outside use:

1. server truth: how to verify that the server is genuinely healthy, reachable, and still using the intended topology
2. worker/session truth: whether all official workers are actually usable through the real remote path, not just one successful `wife` proof
3. public API truth: how other clients should call this service without depending on raw `:4010`, localhost assumptions, or internal-only routes

This phase exists to turn those truths into an explicit, repeatable, documented boundary.

This phase covers:

1. creating a deliberate server verification path for service health, autostart, ingress truth, and topology truth
2. checking every official worker (`dad`, `wife`, `shared-1`, `shared-2`, `shared-3`, `shared-4`) through the real remote topology
3. creating one deliberate external ingress/API path for non-household clients
4. documenting the public API contract and operational restart/status path cleanly

This phase does not cover:

- replacing the browser-runtime layer with a Linux-native or headless runtime
- billing, quotas, or public SaaS product access control
- changing the current relay model away from managed ChatGPT browser workers
- full rollout smoke confidence across the product; that remains Phase 11

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** The Linux remote relay on `77.66.186.75` is real and should be treated as the production orchestration boundary.
- **D-02:** The current proven runtime topology is still `separate_host_runtime_via_reverse_tunnel`.
- **D-03:** Raw `:4010` reachability is not the same thing as a finished outside-client API.
- **D-04:** Secrets, passwords, bearer tokens, and tunnel credentials must stay out of tracked repo files and `.planning`.
- **D-05:** `compact visible` remains the proven browser-runtime baseline during this phase.

### Public API Readiness Direction

- **D-06:** Other clients should consume one deliberate public entrypoint, not direct internal admin or worker routes.
- **D-07:** Public API auth remains bearer-token based in this phase; broader client/account auth is deferred.
- **D-08:** The public path should be fronted deliberately, not by assuming the raw relay port is acceptable as-is.
- **D-09:** Public API docs must explain the current topology truth honestly: remote relay on Linux, runtime on a separate Windows host.

### Session Verification Direction

- **D-10:** Worker/session verification must run through the real remote relay path, not by only checking local browser windows.
- **D-11:** Each official worker should end this phase with an explicit classification such as `usable`, `auth_required`, `bootstrap_failed`, or `relay_failed`.

### the agent's Discretion

- Exact external ingress implementation (`nginx` or equivalent) as long as it is deliberate and documented
- Exact port choice for the public relay edge if the audited host already has occupied standard ports
- Exact format of the operator verification script outputs

</decisions>

<specifics>
## Specific Ideas

- The fastest honest server verification path is a dedicated operator script that checks:
  - `systemctl is-active`
  - `journalctl`
  - local relay `health`
  - external ingress truth
  - current topology hint
- The cleanest worker/session audit is a pinned worker-by-worker remote-relay smoke matrix, not one generic global health call.
- The public API path should likely put a reverse proxy in front of the relay and keep the raw service behind it.
- The final artifact of this phase should answer two different questions separately:
  1. "Is the relay server healthy?"
  2. "Can another client actually call it through the intended public path?"

</specifics>

<deferred>
## Deferred Ideas

- End-user account/auth system for many outside consumers
- Public rate-limiting, billing, and quotas
- Full OpenAPI/SDK ecosystem beyond what is necessary for one clear documented external API contract

</deferred>
