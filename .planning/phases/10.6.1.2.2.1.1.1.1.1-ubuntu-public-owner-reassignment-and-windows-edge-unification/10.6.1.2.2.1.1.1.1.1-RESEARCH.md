# Phase 10.6.1.2.2.1.1.1.1.1 Research

## Research Question

What is the smallest preserve-first change that can unify the real public owner of `77.66.186.75` without risking the 9 live Windows accounts?

## Short Answer

Recommended strategy:

1. Keep Ubuntu as the real public owner because `77.66.186.75` already terminates there today.
2. Remove or override the conflicting Ubuntu `server_name 77.66.186.75` ownership that currently sends public traffic into the wrong vhost.
3. Make Ubuntu the deliberate API owner for the public IP.
4. Proxy only the API routes onward to one Windows-side internal edge path.
5. Prove the unified path with canary `shared-6` before any broader promotion.

This is safer than moving the public contract directly onto the Windows host.

## Why This Is The Recommended Path

### 1. Live evidence already says Ubuntu owns the public IP

The previous phase proved:

- public `77.66.186.75` returns from Ubuntu `nginx`
- Windows `Caddy` is alive only on the LAN-side host path

So the smallest truthful fix is to reconcile ownership where it already lives:

- on Ubuntu

### 2. `nginx` server matching explains the current conflict

Official `nginx` request-processing docs say:

- `nginx` first matches address/port
- then matches the request `Host` against `server_name`
- `default_server` only handles requests whose host does not match a named server

That fits the live evidence exactly:

- Ubuntu has a vhost explicitly claiming `server_name 77.66.186.75`
- so that vhost wins before the relay default server can help

Primary source:

- https://nginx.org/en/docs/http/request_processing.html

### 3. `proxy_pass` is the right primitive for unifying the owner path

Official `nginx` docs confirm that `proxy_pass` is the standard way to forward selected routes to another upstream.

That means Ubuntu can remain the public owner while proxying:

- `/healthz`
- `/api/relay/*`
- `/v1/*`

to a Windows-side internal edge path.

Primary source:

- https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass

### 4. `Caddy reverse_proxy` is already the right Windows-side abstraction

Official `Caddy` docs confirm `reverse_proxy` is the right building block for keeping the Windows public API contract behind one edge while hiding backend details.

That means Windows can keep one deliberate internal edge without opening raw worker or controller ports.

Primary source:

- https://caddyserver.com/docs/caddyfile/directives/reverse_proxy

### 5. MikroTik/NAT is not the best first move here

Official MikroTik docs matter for one reason:

- NAT changes affect new connections and can require fresh probes or conntrack awareness

But because the current real public IP already terminates on Ubuntu, pushing the first preserve-first change down into NAT or direct Windows public ownership would be a larger blast radius than necessary.

Primary source:

- https://help.mikrotik.com/docs/spaces/ROS/pages/3211299/NAT

## Recommended Execution Shape

### Preferred owner model

- Ubuntu remains the public owner of `77.66.186.75`
- Ubuntu serves or proxies the deliberate public API contract
- Windows remains the preserved runtime/API edge behind that owner

### What must change on Ubuntu

- remove or override the conflicting public-IP ownership in the unrelated vhost
- create one deliberate IP-owner path for `77.66.186.75`
- preserve unrelated hostname-based Ubuntu sites
- keep rollback explicit

### What may need to change on Windows

- if Ubuntu cannot safely consume the current Windows edge as-is, add the smallest internal-only Windows edge adjustment needed for Ubuntu to proxy into it
- do not widen exposure of raw `4040`, worker-agent ports, or raw public `:4010`

## Rejected Or Lower-Priority Alternatives

### A. Reassign public IP directly to Windows first

Why not first:

- bigger ingress blast radius
- more likely to entangle unrelated public ownership and NAT
- less preserve-first than correcting the already-live public owner

### B. Keep split ownership and only “fix TLS”

Why not:

- wrong layer
- ownership is broken before TLS semantics matter

### C. Expose raw Windows API/controller ports publicly

Why not:

- violates preserve-first boundary
- violates existing internal-only topology rules

## Planning Implications

This phase should be broken into three waves:

1. Ubuntu owner strategy, rollback, and repo-backed edge assets
2. Deliberate owner reassignment plus canary proof on `shared-6`
3. Independent outside proof, docs/state sync, and Phase 11 verdict

## Research Verdict

The best preserve-first plan is:

- keep Ubuntu as the real public owner
- make that ownership deliberate for `77.66.186.75`
- unify the Windows edge behind it
- use canary `shared-6` as the only required worker-backed proof until the public contract is actually coherent
