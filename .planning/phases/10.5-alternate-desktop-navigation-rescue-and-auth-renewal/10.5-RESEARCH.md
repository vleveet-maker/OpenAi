## Summary

Phase 10.4 already proved that the current alternate-desktop runtime is not failing in one vague way. It is failing in two bounded ways:

1. `dad` is an auth-renewal problem
2. `wife` and `shared-1` are navigation/bootstrap problems

That split strongly suggests Phase 10.5 should stop mixing maintainer proof, operator action, and runner logic together.

The best rescue shape is:

- make alternate-desktop validation callable from the control plane
- fix the current navigation/bootstrap path so it can recover from a stale or wrong initial page
- rerun bounded proof in a deliberate order: `wife`, `dad`, then `shared-1`

The runner evidence shows that `bootstrap_navigation_failed` currently happens too early to tell whether the alternate-desktop browser attached to the wrong page, reused a stale tab, or simply never reached a usable ChatGPT surface after CDP attach. Playwright's navigation guidance is relevant here: navigation and loading are separate, and locator-based checks should remain tied to what the user-facing surface actually exposes rather than brittle DOM chains. The repo already follows that direction with centralized selector maps and `getByRole`/test-id-based candidates, so Phase 10.5 should preserve that pattern instead of rewriting the bootstrap stack.

The control-plane gap is equally clear. `manual-auth/complete` currently starts `alternate_desktop` and marks validation pending, but the actual proof still lives in a PowerShell script. That means the operator-facing truth is one step behind the real runtime truth. The cleanest next move is to make the host-controller own a machine-readable validation endpoint that wraps the canonical probe script, then let `control-api` and `/internal/admin` expose that as a first-class operator action.

The right success threshold also stays narrow: one worker. `wife` is the best primary navigation-rescue target because auth is already out of the way. `dad` should be handled through the new visible-auth plus validation flow. `shared-1` should confirm that the navigation rescue is not overfit to one profile.

**Primary recommendation:** plan Phase 10.5 as three waves:
1. navigation rescue and evidence hardening in the existing bootstrap path
2. control-plane validation and auth-renewal wiring
3. bounded live proof, docs, and explicit unblock-or-stay-blocked decision

## Architecture Patterns

### Pattern 1: Validation Must Move Into The Control Plane
**What:** wrap the canonical alternate-desktop probe in a `host-controller` endpoint and surface it through `control-api`.

**When to use:** after visible auth completes, and any time an operator wants to confirm whether a worker really re-entered usable non-visible runtime.

**Why:** the project already proved that runtime truth and “worker process is alive” are not the same thing.

**Recommended shape:**
```text
/internal/workers/:id/manual-auth/complete
  -> start alternate_desktop
  -> worker shows validationPending

/internal/workers/:id/validate-runtime
  -> host-controller runs test-alternate-desktop-runtime.ps1
  -> response returns machine-readable proof
  -> registry status becomes ready / reauth_required / reachable_but_unusable
```

### Pattern 2: Navigation Rescue Should Prefer Evidence Over Guesswork
**What:** make bootstrap navigation choose a better page and retry in a bounded way before giving up.

**When to use:** immediately after attaching to the alternate-desktop CDP context.

**Why:** `bootstrap_navigation_failed` is currently too early and too coarse to guide maintenance.

**Recommended rescue ladder:**
```text
1. reuse an existing ChatGPT page if one already exists
2. otherwise create a fresh page
3. try goto(startUrl)
4. if that fails, retry once on a fresh page
5. record url/title/branch in stepDetail before returning bootstrap_navigation_failed
```

### Pattern 3: Worker Status Must Reflect Validation Outcome, Not Hope
**What:** distinguish `validation_pending`, `auth_required`, and `reachable_but_unusable after validation`.

**When to use:** after alternate-desktop validation returns.

**Why:** a worker that just restarted is not the same as a worker that proved `phase11Ready=true`.

### Pattern 4: One Passing Worker Unblocks, But The Decision Must Name It
**What:** update roadmap/state only from a written proof-backed decision that names the passing worker.

**When to use:** at the end of the bounded Phase 10.5 proof sequence.

**Why:** the project already learned that vague optimism creates more operator stress later.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| runtime validation | a second ad hoc shell-only proof flow | one canonical probe behind a control-plane endpoint | keeps operator and maintainer truth aligned |
| navigation rescue | CSS/XPath sprawl across runner branches | centralized selector map plus branch-aware navigation evidence | keeps future drift maintenance contained |
| auth renewal | invisible retries after visible login | explicit visible auth, complete, validate sequence | auth loss is still a product-risk signal |

## Common Pitfalls

### Pitfall 1: Treating `bootstrap_navigation_failed` As A Pure Selector Problem
**What goes wrong:** more selectors get added, but the page selection and retry shape stays wrong.
**How to avoid:** capture branch-specific navigation evidence first, then adjust selectors only where the surface actually changed.

### Pitfall 2: Leaving Dad's Auth Renewal Outside The Control Plane
**What goes wrong:** the operator completes visible auth, but there is still no first-class validate step, so runtime truth lags behind manual actions.
**How to avoid:** expose validation as an API-backed operator action.

### Pitfall 3: Using `shared-1` As The First Rescue Target
**What goes wrong:** time is spent chasing the noisiest profile instead of the clearest one.
**How to avoid:** rescue `wife` first, renew `dad` second, use `shared-1` as confirmation.

## Open Questions

1. **Should validation update worker status immediately or only write proof rows?**
   - Recommendation: update worker status immediately and still append proof rows; the operator surface needs the same truth the maintainer log gets.

2. **Should the validation endpoint run the full relay proof or stop at fresh-chat bootstrap?**
   - Recommendation: keep the full canonical proof for `phase11Ready`; it is the milestone gate already.

3. **Should `manual-auth/complete` auto-run validation?**
   - Recommendation: no. Start the runtime and set `validationPending=true`, then let the operator or maintainer run a deliberate validate action. This keeps manual login timing separate from proof timing.
