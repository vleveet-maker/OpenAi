# Phase 10.5: Alternate desktop navigation rescue and auth renewal - Context

**Gathered:** 2026-03-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 10.4 already proved that the selected `alternate_desktop` runtime is failing in two bounded ways:

- `dad` -> `bootstrap_auth_required` at `auth_check`
- `wife` and `shared-1` -> `bootstrap_navigation_failed` at `navigation`

That means Phase 10.5 is not another runtime-search phase. It is the last bounded rescue phase before we either resume Phase 11 or explicitly admit that the selected runtime is still not rollout-ready.

This phase covers:

1. navigation rescue for `wife` and `shared-1` inside the existing `alternate_desktop` bootstrap path
2. a clean auth-renewal and revalidation path for `dad`
3. control-plane wiring so validation is no longer only a manual PowerShell maintainer step
4. a written worker-by-worker runtime decision at the end of the phase

This phase does not cover:

- reopening `hidden_runtime` or Docker/Xvfb as primary candidates
- CAPTCHA bypass, stealth, or anti-detection tooling
- a new mobile product UI
- Phase 11 rollout smoke itself

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** Phase 10.5 is the last rescue attempt for the selected `alternate_desktop` runtime before further architectural reconsideration.
- **D-02:** Success still means one worker reaching `phase11Ready=true`; we do not need all three perfect before Phase 11 can resume.
- **D-03:** `wife` is the primary navigation-rescue target because it is already past auth.
- **D-04:** `dad` is the primary auth-renewal target because its remaining tail is clearly `bootstrap_auth_required`.
- **D-05:** `shared-1` is the confirmation target for the navigation rescue, not the first selector-debug target.

### Runtime Policy

- **D-06:** Visible browser use remains manual-only for first login or reauthentication.
- **D-07:** Routine steady-state work must stay non-visible on the operator's main desktop.
- **D-08:** The same durable profile used in visible auth must be the one revalidated in `alternate_desktop`.
- **D-09:** If visible auth succeeds but non-visible runtime still fails, treat that as runtime evidence, not as a cue to silently keep retrying.

### Control-Plane Policy

- **D-10:** Validation after `Complete login -> non-visible runtime` should become a first-class operator/control-plane action, not only a maintainer shell ritual.
- **D-11:** Navigation failure, auth failure, and successful non-visible validation must stay distinct in worker status and proof artifacts.
- **D-12:** Roadmap/state may only unblock Phase 11 from written proof that names the passing worker.

### Explicit Non-Goals

- **D-13:** Do not introduce a new browser runtime in this phase.
- **D-14:** Do not add public-facing product features here.
- **D-15:** Do not hide a failed rescue behind optimistic `ready` status language.

### the agent's Discretion

- Exact shape of the validation endpoint and whether it lives primarily in `host-controller` or `control-api`
- Exact navigation rescue ladder inside the current bootstrap runner
- Exact artifact names for additional proof rows, worker validation summaries, and unblock-decision wording

</decisions>

<specifics>
## Specific Ideas

- The strongest missing operator capability is not a new runtime button; it is a truthful `Validate non-visible runtime` step after login completion.
- Navigation rescue should stay inside the existing bootstrap path and be based on better page selection, retry shape, and evidence, not on scattering new selectors across unrelated files.
- `wife` should be the first target for proving non-visible bootstrap again because it avoids auth noise.
- `dad` should be the first worker to exercise the renewed visible-auth-to-validation flow.
- If Phase 10.5 still cannot get one worker to `phase11Ready=true`, the project should say so explicitly and stop pretending Phase 11 is “almost there”.

</specifics>
