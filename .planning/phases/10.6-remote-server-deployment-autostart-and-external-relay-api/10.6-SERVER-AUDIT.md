## Topology Evidence

The browser runtime is not on the Linux server itself.

The proven working path is:

1. `owmcgp-remote-relay` runs on `77.66.186.75`
2. a Windows worker such as `wife` runs locally in `compact visible`
3. the Linux server reaches that worker through a server-local forwarded port like `127.0.0.1:14022`
4. the forwarding is provided by a reverse SSH tunnel from the Windows host

This means the verified topology is `separate_host_runtime_via_reverse_tunnel`.

## Public Ingress Truth

Raw public ingress on `:4010` is not yet a clean public entrypoint.

Observed facts:

- service listens on `0.0.0.0:4010`
- localhost calls on the server work
- server self-call to `http://77.66.186.75:4010/...` failed
- direct local-machine call to `http://77.66.186.75:4010/...` timed out during verification
- `ufw` is inactive, so this is not explained by a simple local firewall rule

## Topology Verdict

**Verdict:** `remote relay deployed and working; browser runtime remains separate-host; raw public ingress on :4010 is not the proven caller path yet`

Implications:

- the remote orchestration module is real and operational on the server
- autostart is real
- the authenticated relay API is real
- the proven runtime path is `server-local API + reverse tunnel + compact-visible Windows worker`
- if public internet clients should call this service directly next, the project should front it with a stable ingress layer such as Nginx on an allowed public port or an explicit SSH tunnel
