## Summary

The codebase already has two strong building blocks:

1. `control-api` already owns the useful product contract:
   - timed sessions
   - fresh-chat bootstrap
   - relay orchestration
   - worker assignment and lifecycle truth
2. `host-controller` is already a network-callable controller with token-authenticated HTTP routes

That makes `control-api` the cleanest extraction target. The remote server should host a standalone `control-api` mode plus a dedicated relay facade, not a second orchestration stack.

## What The Code Already Proves

### Pattern 1: `control-api` Already Knows The Product Workflow

Current route and service layout shows that `control-api` already owns:

- session creation and pinning
- bootstrap gating before composer unlock
- chat relay lifecycle
- worker/runtime truth

Planning implication:

- remote extraction should add a narrow relay API on top of this layer
- it should not bypass the orchestration by talking directly to browser workers from a new service

### Pattern 2: `host-controller` Already Gives A Remote-Friendly Control Boundary

`host-controller` already exposes an authenticated HTTP API and is already consumed through `host-controller-client.ts`.

Planning implication:

- the remote relay service can keep using this pattern instead of inventing a new control channel
- the final topology verdict must state whether the remote server reaches the runtime locally or over this existing controller boundary

### Pattern 3: Current Public App Routes Are Too Client-Specific For Reuse

Current public routes are shaped for the shared-screen app and session-client lifecycle. They are awkward for a generic external caller that only wants:

- ask something in a fresh dialog
- continue an existing dialog
- end a dialog

Planning implication:

- Phase 10.6 should add a thin dedicated API such as:
  - `GET /api/relay/health`
  - `POST /api/relay/ask`
  - `POST /api/relay/dialogs/:dialogId/end`

### Pattern 4: The Final Question Is Topology Truth, Not Only Deployment Success

Even if the service starts on the remote host, the phase is incomplete unless it answers:

- does the remote relay reach the compact-visible runtime directly on that host
- or does it call into another existing host/runtime boundary
- or is that still blocked today

Planning implication:

- Phase 10.6 must end with a topology verdict artifact, not just a deployed service

## Recommended API Contract

### `GET /api/relay/health`

Purpose:
- confirm the remote relay process is alive and knows its mode

Recommended response:

```json
{
  "ok": true,
  "service": "owmcgp-remote-relay",
  "mode": "remote_relay",
  "topology": "pending"
}
```

### `POST /api/relay/ask`

Purpose:
- create a fresh dialog or continue an existing dialog and return the assistant reply

Recommended request:

```json
{
  "requestedForLabel": "remote-user",
  "dialogId": null,
  "newDialog": true,
  "messageText": "Hello",
  "timeoutMs": 180000
}
```

Recommended response fields:

- `dialogId`
- `sessionId`
- `workerId`
- `conversationMode`
- `modelLabel`
- `assistantReplyText`
- `relayResult`

### `POST /api/relay/dialogs/:dialogId/end`

Purpose:
- end the dialog/session explicitly from the remote caller side

## Common Pitfalls

### Pitfall 1: Calling The Whole Browser Runtime "moved"
The current proven thing is the orchestration layer plus the runtime contract, not proof that a server-hosted headless browser path is already equivalent.

### Pitfall 2: Reusing Shared-Screen Routes As The External API
That would leak client-specific lifecycle assumptions into what should be a simpler remote service boundary.

### Pitfall 3: Writing Passwords Or Tokens Into Repo State
The phase needs deploy assets and env contracts, but secrets must stay out of tracked files.

### Pitfall 4: Treating `systemd` As Guaranteed
The host audit should verify this before the deploy script treats it as fact.
