# Phase 10.6: Remote server deployment, autostart, and external relay API - Context

**Gathered:** 2026-03-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 10.5.1.1.1 gave the project a practical runtime baseline:

- compact visible proof passed on `dad`, `wife`, `shared-1`, `shared-2`, `shared-3`, and `shared-4`
- the current working path is no longer blocked by alternate-desktop research
- windows can stay closed until needed, but the working orchestration still lives on the operator machine

This phase exists to separate the useful orchestration module from the local desktop and move it onto the dedicated server.

This phase covers:

1. extracting the proven relay/session/bootstrap orchestration layer to a standalone remote-service shape
2. preparing host audit, deployment, and autostart assets for the dedicated SSH server
3. exposing one authenticated remote API so external callers can ask for a fresh or continuing dialog and get the reply back
4. ending with a written topology verdict that says exactly how the remote service reaches the browser-runtime layer

This phase does not cover:

- pretending the compact-visible browser runtime itself is already fully relocated or headless-safe on the server
- replacing browser relay with direct OpenAI API usage
- changing the household product UX
- billing, entitlements, or public SaaS work
- Phase 11 rollout smoke itself

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** The extractable module is the `control-api`-centered relay/session/bootstrap orchestration layer, not the full browser-runtime stack.
- **D-02:** The target server for this phase is `ssh -p 2222 mi50@77.66.186.75`.
- **D-03:** Passwords, tokens, proxy links, and runtime secrets must stay out of tracked repo files and `.planning` artifacts.
- **D-04:** This phase must end with topology truth, even if that truth says the remote relay still depends on another host for the browser-runtime layer.

### Remote Service Contract

- **D-05:** The first remote API surface should stay narrow:
  - `GET /api/relay/health`
  - `POST /api/relay/ask`
  - `POST /api/relay/dialogs/:dialogId/end`
- **D-06:** Remote API auth uses `Authorization: Bearer <REMOTE_RELAY_API_TOKEN>`.
- **D-07:** `POST /api/relay/ask` should support both fresh and continuing dialog calls without exposing the current public shared-screen routes directly.
- **D-08:** The response contract should expose at least `dialogId`, `sessionId`, `workerId`, `conversationMode`, `modelLabel`, `assistantReplyText`, and `relayResult`.

### Deployment Contract

- **D-09:** Assume a Linux host with `systemd` until the host audit proves otherwise.
- **D-10:** Planned remote layout:
  - service name: `owmcgp-remote-relay`
  - app dir: `/opt/owmcgp-remote-relay`
  - env file: `/etc/owmcgp/remote-relay.env`
  - data dir: `/srv/owmcgp-remote-relay`
- **D-11:** The deploy path should be scriptable from the current workstation, but the script must not embed the password in repo state.

### Explicit Non-Goals

- **D-12:** Do not silently downgrade to an unproven headless runtime just because the service moved to the server.
- **D-13:** Do not rewrite the current compact-visible runtime decision during this phase.
- **D-14:** Do not expose raw internal admin or worker-control routes as the public remote API.

### the agent's Discretion

- Exact naming of the standalone `control-api` mode
- Exact payload shape for health detail versus minimal public health
- Exact wording of the topology verdict if the remote host can only front the orchestration layer and not the browser-runtime layer directly

</decisions>

<specifics>
## Specific Ideas

- The cleanest extraction target is the already-proven orchestration layer, because it already owns session creation, fresh-chat bootstrap gating, and relay coordination.
- The current public session/chat routes are shaped for the shared-screen client, not for a generic remote caller, so Phase 10.6 should add a thin dedicated relay API rather than reusing those routes directly.
- A host-audit script should capture OS, init system, Node availability, disk, memory, and browser/runtime clues before deployment assets assume too much.
- The final artifact must say one of three things:
  1. the remote relay reaches the runtime directly on the same host,
  2. the remote relay reaches a separate existing host that still owns the runtime,
  3. or the topology is blocked by a precise incompatibility that must be solved before relying on the remote API.

</specifics>
