# Phase 10.6.1.2.2.1 Context

## Summary

This phase is not about rebuilding the Windows browser block and not about touching the 9 live ChatGPT accounts.

The real problem is narrower:

- the deployed Windows Server already has the valuable browser state
- the Windows-side `control-api` can run locally
- but the public edge on that host is still mismatched:
  - `:4010` is closed from the network point of view
  - `80/443` currently resolve through `Caddy`
  - that `Caddy` path is not yet our verified API path

So the next correct step is preserve-first edge reconciliation.

## Current Truth

- The deployed Windows Server host is `192.168.88.250`.
- `host-controller` is reachable on `http://192.168.88.250:4040`.
- The deployed host already has the 9-worker inventory:
  - `dad`
  - `wife`
  - `shared-1`
  - `shared-2`
  - `shared-3`
  - `shared-4`
  - `shared-5`
  - `shared-6`
  - `shared-7`
- Direct public API promotion is still blocked by edge truth:
  - `192.168.88.250:4010` was observed closed
  - `http://192.168.88.250/healthz` and `/v1/models` return `308`
  - the HTTP server identifies as `Caddy`
- The previous phase already proved preserve-first canary and subset worker control.
- The previous phase also proved a local shadow API path on `127.0.0.1:4012` with a canary worker.

## Locked Decisions

- Do not delete, reset, overwrite, or mass-relogin the 9 deployed browser profiles.
- Do not treat the deployed Windows Server as a disposable redeploy target.
- Do not expose `host-controller` or worker-agent ports as the public API.
- Do not treat raw `:4010` exposure as mandatory if a safer `Caddy -> 127.0.0.1:4010` path is available.
- Use staged cutover:
  1. capture edge truth and backup
  2. prove a shadow path on one canary worker
  3. promote only if external proof succeeds
- If the promoted edge still cannot be proven safely, keep the verdict as a hold rather than forcing a broad switch.

## Phase Goal

Activate a deliberate Windows-side public API edge on the already-deployed Windows Server by reconciling the current `Caddy`/`:4010` mismatch, while keeping the 9 live accounts untouched.

- Keep the browser block runtime and API activation separate.
- Prefer loopback binding plus reverse proxy over directly spraying more public listeners.
- Preserve the existing `Caddy` edge if it can be reconciled safely and rolled back cleanly.
- Preserve the current MikroTik path unless the Windows-side audit proves a smaller change is safer.

## Deferred Ideas

- Replatforming away from `Caddy` is deferred unless the audit proves it is the blocker and not just misconfigured.
