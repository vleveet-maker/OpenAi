# Phase 10.6.1.2.2.1 Research

## Findings

### 1. The blocker is now the Windows-side edge, not the browser accounts

The previous preserve-first phase already proved the important things:

- the deployed Windows Server really contains the 9 live accounts
- one-worker and subset canary control is safe
- a shadow API path can answer locally without touching the whole pool

That means this phase should not spend effort on browser recovery first. The smaller and more honest target is the public edge itself.

### 2. The mismatch is specific and actionable

Current deployed truth is narrow enough to plan around:

- `host-controller` is reachable on `192.168.88.250:4040`
- `192.168.88.250:4010` is closed externally
- `80/443` answer through `Caddy`
- current `Caddy` behavior is a `308` redirect path rather than a proven relay/API edge

So the next phase is not "make API exist". The API already exists locally. The next phase is:

1. discover the exact `Caddy` ownership and config path
2. back it up
3. prove a shadow path
4. promote or hold with evidence

### 3. Preserve-first promotion should prefer loopback plus reverse proxy

The safest promoted shape for a deployed Windows host with valuable browser state is:

- keep `control-api` on `127.0.0.1:4010` or a nearby loopback shadow port
- let the edge process own `80/443`
- forward only the deliberate public routes to the local API

That keeps internal ports private and makes rollback much smaller than exposing more raw listeners.

### 4. `Caddy` is a good fit if we change it gracefully

Official `Caddy` docs confirm two useful properties:

- `reverse_proxy` cleanly forwards requests to a local upstream such as `localhost:4010`
- `caddy reload` is the recommended zero-downtime config change path, and Caddy rolls back if the new config fails to load

For this phase, that strongly suggests:

- do not restart `Caddy` blindly
- prefer config backup plus `validate/reload`
- make the shadow path and promoted path explicit and reversible

### 5. Shadow-first proof should include both local and outside-client checks

It is not enough to prove only:

- `http://127.0.0.1:4011/healthz`

The phase must separate two truths:

1. local Windows-side API truth
2. public edge truth

That means the safest progression is:

1. prove local shadow path on one canary worker
2. prove the edge path locally on the deployed host
3. prove the same edge path from outside the NAT boundary

### 6. The phase should keep host-controller and worker ports private

Nothing in the current evidence suggests `4040` or `4021..` should become public.

The deliberate public boundary should stay:

- `healthz`
- `api/relay/health`
- `v1/models`
- `v1/chat/completions`

Everything else should remain internal.

## Planning Implications

- Add requirement IDs specifically about edge truth, shadow path, promoted path, and outside proof.
- Plan around the deployed Windows host first, not local machine assumptions.
- Make backup, config ownership, and rollback first-class deliverables.
- Use canary `shared-6` or another explicitly allowlisted worker for promoted-path proof.
- End with one explicit verdict: `safe_to_promote`, `safe_but_hold`, or `hold_preserve_accounts`.

## Recommended Execution Order

1. Capture current `Caddy` service/config/listener truth and back it up.
2. Implement or harden a shadow Windows-side public API path behind a reversible edge config.
3. Prove canary flow locally, then through the real public edge, then decide whether promotion is safe.
