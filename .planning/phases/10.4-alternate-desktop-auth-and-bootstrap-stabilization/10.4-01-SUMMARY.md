# Phase 10.4 Plan 01: Summary

The worker and control plane now treat bootstrap evidence as a first-class signal instead of overloading relay failure fields.

## Accomplishments

- Added explicit bootstrap telemetry to the worker runtime: `lastBootstrapAt`, `lastBootstrapFailureCode`, `lastBootstrapStep`, and `lastBootstrapUsability`.
- Extended the bootstrap result contract with step-level metadata so later hardening can say exactly where `alternate_desktop` stalls.
- Stopped writing bootstrap failures into `lastRelayFailureCode`; relay telemetry now remains relay-only.
- Surfaced the new bootstrap fields on `/internal/workers` and updated registry persistence plus health-monitor capability classification around bootstrap evidence such as `bootstrap_auth_required` and `temporary_confirmation_not_found`.

## Key Decisions

- Keep `runtimeCapability=usable` reserved for workers that have real relay-success evidence; bootstrap-only success still shows as reachable but not rollout-proven.
- Treat missing bootstrap evidence as different from relay failure so Phase 10.4 can distinguish auth loss, bootstrap drift, and assignment noise cleanly.

## Verification

- `cmd /c npm.cmd test --prefix workers/agent`
- `cmd /c npm.cmd test --prefix services/control-api`

## Residual Risk

- Bootstrap steps are now visible, but the bootstrap runner still needs composer-ready gating and richer step detail before Phase 11 can use alternate-desktop proof as rollout confidence.
