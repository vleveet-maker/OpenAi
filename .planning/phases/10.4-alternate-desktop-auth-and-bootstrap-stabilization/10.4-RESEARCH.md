## Summary

The fastest credible unblock is not another browser-runtime experiment. The live evidence already narrowed the problem to three bounded tails inside the selected `alternate_desktop` runtime:

1. `dad` still surfaces `bootstrap_auth_required`
2. `wife` gets deep enough into fresh-chat bootstrap to fail at `temporary_confirmation_not_found`
3. `shared-1` never proves usability cleanly because the isolated proof is still coupled too tightly to assignment timing

That means the phase should be planned as a stabilization stack, not a redesign stack:

- first, make auth state explicit immediately after `visible_auth -> alternate_desktop`
- second, make bootstrap failure points explicit enough to harden the right selector step instead of only reporting one coarse failure
- third, make the proof path isolate runtime usability from assignment noise so `phase11Ready=true` means something precise

The current code already gives a strong base. `temporary-chat-runner.ts` distinguishes `bootstrap_auth_required`, `bootstrap_challenge_detected`, `temporary_confirmation_not_found`, `model_picker_not_found`, and `model_option_not_found`. The best next step is therefore not a new runner, but deeper step telemetry and better gating around the existing runner:

- detect whether new-chat click happened
- detect whether temporary entry click happened
- detect whether temporary confirmation appeared
- detect whether onboarding dismiss happened
- detect whether preferred model was selected
- detect whether the composer is actually usable

The auth side should follow the same principle. `manual-auth/complete` currently restarts the worker into `alternate_desktop`, but the decisive truth is delayed until a later proof. Phase 10.4 should plan for an immediate post-transition validation pass that can set the worker to one of three meaningful states:

- `ready` because bootstrap on the selected runtime succeeded
- `reauth_required` because the durable profile no longer yields a usable authenticated surface
- `ready_but_bootstrap_failed` or equivalent evidence-backed degraded state because auth is fine but fresh-chat automation drift remains

The proof side should also be narrowed. `shared-1` currently proves that controller timing can obscure runtime truth. The stabilization phase should separate:

- runtime attach / health truth
- bootstrap truth
- relay truth
- session assignment truth

so that an assignment timeout does not erase useful bootstrap evidence.

**Primary recommendation:** Plan Phase 10.4 as three stabilization waves:
1. control-plane truth and proof decomposition
2. auth recovery and bootstrap-step hardening
3. bounded live proof and explicit Phase 11 unblock-or-block decision

## Architecture Patterns

### Pattern 1: Post-Transition Validation Must Be Immediate
**What:** Validate auth and bootstrap immediately after `manual-auth/complete` restarts the worker in `alternate_desktop`.

**When to use:** Right after `visible_auth -> alternate_desktop`.

**Why:** The operator just completed a manual login, so this is the narrowest window to tell whether the durable profile survived the runtime handoff.

**Example shape:**
```text
manual-auth/complete
  -> start alternate_desktop
  -> wait for worker health
  -> run bounded bootstrap validation
  -> set status to ready / reauth_required / degraded-with-bootstrap-failure
```

### Pattern 2: Bootstrap Failure Should Be Step-Specific
**What:** Break the existing `temporary_confirmation_not_found` tail into observable substeps.

**When to use:** Inside the current bootstrap runner and proof script.

**Why:** `temporary_confirmation_not_found` is already much better than generic failure, but still too coarse for low-stress maintenance.

**Recommended step markers:**
```text
newChatOpened
temporaryEntrySelected
temporaryConfirmed
temporaryOnboardingDismissed
modelSelected
composerReady
```

### Pattern 3: Proof Modes Must Isolate Runtime Truth From Assignment Truth
**What:** Allow the proof path to report meaningful bootstrap evidence even if assignment timing is noisy.

**When to use:** In `test-alternate-desktop-runtime.ps1` and any control-plane snapshot it depends on.

**Why:** `shared-1` currently demonstrates that `assignment timeout` is not the same problem as `auth_required` or `bootstrap drift`.

### Pattern 4: Unblock Phase 11 Only On One Known-Good Worker
**What:** The success threshold for this phase is one worker with `phase11Ready=true`, not perfection across all three.

**When to use:** In planning, verification, and final runtime-decision wording.

**Why:** The milestone is rollout stability, not household-wide perfection before smoke even starts.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Auth recovery | A hidden silent retry loop | Explicit `visible_auth -> alternate_desktop -> validate` path | Auth loss is a product-risk signal, not something to bury |
| Bootstrap drift | Ad hoc locator fixes inside unrelated runner branches | Centralized selector-map and step telemetry | Keeps future ChatGPT UI drift maintainable |
| Assignment noise | One opaque proof result | Separate runtime, bootstrap, relay, and assignment evidence | Makes Phase 11 gating evidence-backed |
| Phase unblock | "Looks better now" | `phase11Ready=true` plus a written decision | Keeps rollout confidence honest |

## Common Pitfalls

### Pitfall 1: Treating `bootstrap_auth_required` As Only A Cookie Problem
**What goes wrong:** The team assumes the durable profile is broken, when the real issue is post-transition runtime usability.
**How to avoid:** Validate auth immediately after the alternate-desktop transition and record runtime class, page URL, and status together.

### Pitfall 2: Patching `wife` Without Knowing Which Bootstrap Step Broke
**What goes wrong:** More selectors get added, but the real failing step stays hidden behind `temporary_confirmation_not_found`.
**How to avoid:** Emit step-level evidence before broadening selector coverage.

### Pitfall 3: Letting `shared-1` Failures Poison Runtime Conclusions
**What goes wrong:** An assignment timeout is misread as runtime failure.
**How to avoid:** Separate assignment and runtime proof outputs explicitly.

### Pitfall 4: Unblocking Phase 11 On A One-Off Visible Success
**What goes wrong:** A visible-auth run looks good, but routine alternate-desktop flow is still unstable.
**How to avoid:** Only count non-visible `alternate_desktop` proof results toward `phase11Ready=true`.
