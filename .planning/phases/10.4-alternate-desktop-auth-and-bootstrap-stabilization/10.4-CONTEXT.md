# Phase 10.4: Alternate desktop auth and bootstrap stabilization - Context

**Gathered:** 2026-03-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 10.3 already answered the big runtime question. We are no longer comparing hidden runtime, Docker/Xvfb, and alternate desktop as peer candidates. That decision work is done. The selected direction for bounded stabilization is:

- same-session `alternate_desktop`
- visible auth only for manual first login or reauthentication
- routine use only in the non-visible alternate desktop runtime

The remaining work is narrower and more operational:

1. recover or confirm valid auth on at least one alternate-desktop worker
2. stabilize the current `Temporary Chat` bootstrap path where live proof reached `temporary_confirmation_not_found`
3. tighten evidence and operator truth until at least one worker records `phase11Ready=true`, or else keep Phase 11 blocked with explicit proof

This phase is specifically about the known live tails:

- `dad` -> `bootstrap_auth_required`
- `wife` -> `temporary_confirmation_not_found`
- `shared-1` -> isolated proof timed out before successful assignment

This phase covers:

- bounded auth recovery flow on the selected runtime
- bootstrap stabilization for current `Temporary Chat` confirmation/onboarding drift
- proof-script and control-plane truth needed to decide whether `Phase 11` can start

This phase does not cover:

- another broad runtime search
- CAPTCHA bypass or anti-detection tooling
- replacing browser relay with direct OpenAI API usage
- the future mobile multi-chat UX
- Phase 11 rollout-smoke UX itself

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** Phase 10.4 is a stabilization phase for `alternate_desktop`, not another runtime exploration phase.
- **D-02:** At least one worker reaching `phase11Ready=true` is sufficient to unblock Phase 11.
- **D-03:** `visible_auth` remains manual-only and must not become the routine steady-state path again.
- **D-04:** If bounded stabilization still fails, the project must keep Phase 11 blocked explicitly instead of treating partial progress as good enough.

### Runtime Policy

- **D-05:** Manual login or reauthentication may still happen in a visible interactive browser.
- **D-06:** Routine household use must stay non-visible on the operator's main desktop.
- **D-07:** The same durable profile authenticated in `visible_auth` must be reused in `alternate_desktop`.
- **D-08:** Auth recovery, bootstrap drift, and assignment-timeout tails must be reported as distinct failure classes.

### Stabilization Priorities

- **D-09:** Prioritize `wife` first for bootstrap stabilization because it already gets past auth and reaches the deepest live bootstrap state.
- **D-10:** Treat `dad` as the auth-recovery proof path for the selected runtime.
- **D-11:** Treat `shared-1` as a control-plane and assignment-proof follow-up, not the first selector-debug target.

### Explicit Non-Goals

- **D-12:** Do not introduce new stealth, CAPTCHA-bypass, or anti-detection layers.
- **D-13:** Do not reopen the rejected `hidden_runtime` or `docker_headed_xvfb` paths as primary solutions.
- **D-14:** Do not expand into Phase 11 rollout history/UI work here.

### the agent's Discretion

- Exact split of work between auth recovery, bootstrap selector hardening, and evidence tightening
- Exact artifact names for new live-proof rows, worker snapshots, or operator-facing status fields
- Exact test granularity, as long as auth, bootstrap, and proof-state regressions are covered

</decisions>

<specifics>
## Specific Ideas

- The best known near-term unblock path is not "make all three perfect"; it is "get one worker to `phase11Ready=true` with bounded evidence."
- `wife` is the best bootstrap-stabilization candidate because the runtime already proves usable enough to reach `temporary_confirmation_not_found` rather than failing at auth.
- `dad` is the best auth-recovery candidate because it isolates the selected runtime's remaining login durability question.
- The proof path should continue emitting runtime matrix rows, but operator-facing state should make it obvious whether the blocker is auth, bootstrap drift, or assignment/flow timing.
- If `Temporary Chat` onboarding or confirmation now appears through a different localized surface, selector maintenance should stay centralized in the bootstrap selector map rather than scattering one-off fixes across runner logic.

</specifics>
