# Phase 10.2: Hidden runtime reliability review and alternative browser runtime decision - Context

**Gathered:** 2026-03-28
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase is an urgent runtime-decision phase for the current household ChatGPT architecture.

It exists because live comparison now proved a materially different outcome between the two runtime classes introduced in Phase 10.1:

1. `visible_auth` on the `wife` durable profile reaches a normal logged-in ChatGPT page
2. `hidden_runtime` on the same profile, and on `dad` plus `shared-1`, falls into a Cloudflare challenge URL during fresh-chat bootstrap and then fails with `new_chat_selector_not_found`

The phase therefore covers:
- deciding whether the current hidden/headless runtime can be stabilized with bounded changes
- reviewing pool/worker control-plane reliability so status is not lying while runtime is degraded
- choosing a concrete alternative runtime path if the current hidden/headless path is not viable

This phase does not add new end-user product scope, does not introduce CAPTCHA bypass or anti-detection tooling, and does not yet build the rollout-smoke surface of Phase 11.

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** The project must treat the `visible_auth` and `hidden_runtime` paths as different runtime classes, not as two equally reliable views over the same saved browser session.
- **D-02:** The current live result is that `visible_auth` works on at least one durable profile while `hidden_runtime` fails on all three workers by landing in Cloudflare challenge flow.
- **D-03:** The project must not explain this away as a pure selector problem. The selector failure is downstream of runtime landing on the wrong page.

### Runtime Policy

- **D-04:** Manual login or reauthentication may remain visible and operator-driven.
- **D-05:** Routine household operation must still be non-visible to the operator, but that does not have to mean the current `headless=true launchPersistentContext()` approach if it proves unreliable.
- **D-06:** If hidden/headless runtime remains unreliable after bounded review, the correct response is an architecture/runtime decision, not an endless sequence of tiny patches.

### Explicit Non-Goals

- **D-07:** Do not add CAPTCHA bypass, stealth browser tooling, or anti-detection stacks in this phase.
- **D-08:** Do not replace the whole product with the OpenAI API in this phase.
- **D-09:** Do not expand into the future mobile multi-chat and image-attachment product work here.

### the agent's Discretion

- Exact shape of the evidence artifact that records whether current hidden runtime is viable
- Exact split between code fixes, runtime experiments, and decision docs
- Exact alternative runtime candidates to compare, as long as they preserve the manual-login policy and non-visible steady-state goal

</decisions>

<specifics>
## Specific Ideas

- Live hidden-runtime probes now produce `pageUrl` values containing `__cf_chl_rt_tk`, which means the runtime is landing in challenge flow before it can even reach the new-chat entrypoint.
- The same `wife` durable profile, when inspected through `visible_auth`, opens a normal logged-in ChatGPT landing page with the standard composer visible.
- `host-controller` currently reports `start_requested` for pool start, but manual worker start reproduced healthier behavior than controller-driven restart during the live check.
- `control-api` and `host-controller` can disagree about pool state (`idle` versus actually running proxy and worker processes), so Phase 11 should not be planned on top of current status semantics without review.

</specifics>
