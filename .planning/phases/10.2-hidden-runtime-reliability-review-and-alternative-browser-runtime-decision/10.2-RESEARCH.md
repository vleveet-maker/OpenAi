## Summary

The current host hidden runtime should be treated as presumptively non-viable for rollout. Local evidence already shows a consistent split: `visible_auth` reaches a normal logged-in ChatGPT page on `wife`, while `hidden_runtime` on `wife`, `dad`, and `shared-1` lands on Cloudflare challenge URLs and then fails bootstrap as `new_chat_selector_not_found`. The code paths are materially different, not just cosmetically different: visible auth starts a native Edge instance and attaches over CDP, while hidden runtime launches a Playwright persistent context with `headless: true` and a custom browser executable path.

Upstream docs reinforce that this is not a normal selector-hardening problem. Cloudflare explicitly documents headless browsers and Playwright-style automation as unsupported challenge environments, and Playwright documents both `executablePath` and `connectOverCDP()` as caveated paths compared with bundled/browser-channel launches and the Playwright protocol. That does not prove every headful automated path will fail, but it does mean Phase 10.2 should not be planned as another patching phase. It should be planned as a bounded runtime decision with artifacts.

The most practical concrete alternative to decide against is a headed-but-non-visible Linux/Xvfb runtime using the project's existing browser-access stack, not a brand-new Windows desktop/session launcher. The repo already has Xvfb/x11vnc/websockify infrastructure, Playwright officially supports headed Linux runs under Xvfb, and this keeps routine household operation non-visible. Because the project has prior evidence that Docker/browser fingerprinting can be worse than host-native, this should still be a proof step, not an assumption. If that proof fails too, Phase 10.2 should end with a decision that v1.2 is blocked on a new host-native headful hidden-runtime design rather than letting Phase 11 proceed on bad foundations.

**Primary recommendation:** Plan Phase 10.2 as a strict "prove current hidden runtime in one bounded pass or pivot to headed Docker/Xvfb" decision phase, with control-plane truth fixes in Wave 1 and the runtime comparison plus decision document in later waves.

### Pattern 1: Separate Reachability From Usability
**What:** Model runtime state in two layers:
- `reachability`: process/port/browser-context presence
- `usability`: actually lands on usable ChatGPT surface and can bootstrap a fresh chat

**When to use:** Everywhere a host pool or worker status is shown, persisted, or used for Phase 11 rollout gating.

**Example:**
```typescript
interface RuntimeEvidenceRow {
  workerId: string;
  runtimeClass: "visible_auth" | "hidden_runtime" | "docker_headed_xvfb";
  processReachable: boolean;
  browserContextReady: boolean;
  chatgptUsable: boolean | null;
  cfMitigatedChallenge: boolean | null;
  pageUrl: string | null;
  bootstrapFailureCode: string | null;
  tracePath: string | null;
  checkedAt: string;
}
```

### Pattern 2: One Evidence Artifact Per Worker/Runtime Attempt
**What:** Every attempt should produce a machine-readable row plus durable artifacts.

**When to use:** For the existing hidden runtime, any single bounded launch variant, and the alternative candidate runtime.

**Example:**
```typescript
const row: RuntimeEvidenceRow = {
  workerId,
  runtimeClass,
  processReachable,
  browserContextReady,
  chatgptUsable,
  cfMitigatedChallenge,
  pageUrl,
  bootstrapFailureCode,
  tracePath,
  checkedAt: new Date().toISOString()
};
```

### Pattern 3: Status Must Follow Capability, Not Just Ports
**What:** `ready` should mean "safe to route Phase 11 smoke traffic", not merely "agent answers `/health`".

**When to use:** In host-controller snapshots, control-api pool summaries, and internal admin wording.

**Example:**
```typescript
type HostRuntimeCapability =
  | "unreachable"
  | "reachable_but_unusable"
  | "usable";

function toRolloutStatus(capability: HostRuntimeCapability): "idle" | "degraded" | "ready" {
  if (capability === "usable") return "ready";
  if (capability === "reachable_but_unusable") return "degraded";
  return "idle";
}
```

### Pattern 4: Binary Runtime Decision Gate
**What:** Phase 10.2 should stop after a small, predefined matrix and then decide.

**When to use:** At phase scope definition and wave planning.

**Example:**
```text
Current host hidden runtime:
- If one bounded re-test still reaches challenge flow -> FAIL current runtime

Primary alternative candidate:
- If one durable profile can complete manual auth, hidden steady-state bootstrap, and relay -> CHOOSE candidate
- If not -> record v1.2 blocked on new host-native headful hidden-runtime phase
```

### Anti-Patterns to Avoid
- **Selector-first diagnosis:** Do not treat `new_chat_selector_not_found` as a DOM drift problem when `pageUrl` already shows challenge flow.
- **Port-based truth:** Do not let `/health`, agent ports, CDP ports, or `browserContextReady` alone imply Phase 11 readiness.
- **Several runtime pivots at once:** Do not compare three or four new runtimes in one phase. Use one bounded rescue attempt for current hidden runtime, one concrete alternative candidate, then decide.
- **Stealth creep:** Do not drift into stealth plugins, CAPTCHA bypass, fingerprint spoofing, or anti-detection experimentation.
- **Assuming Docker is already headed:** The current Docker worker baseline is not explicitly configured as a headed steady-state runtime and would need intentional work before it can serve as the alternative proof.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Challenge detection | Custom DOM-only heuristics for every challenge surface | Cloudflare challenge indicators plus top-level page URL and response header evidence | Cloudflare exposes `cf-mitigated: challenge`; DOM-only guesses are too brittle |
| Browser failure debugging | Ad hoc console logging | Playwright tracing plus `DEBUG=pw:browser` logs | Official tooling already captures browser operations, snapshots, and network |

**Key insight:** This phase is about choosing a runtime with bounded evidence, not about inventing a new browser platform. Reuse official diagnostics and the repo's existing runtime surfaces wherever possible.

## Common Pitfalls

### Pitfall 1: Treating Challenge Flow As UI Drift
**What goes wrong:** The team keeps editing selector maps after the browser never actually reaches the normal ChatGPT surface.
**Why it happens:** The failure surfaces as `new_chat_selector_not_found`, which can look like a DOM drift problem.
**How to avoid:** Record `pageUrl`, challenge header evidence, screenshot, and trace before any selector conclusion.
**Warning signs:** `pageUrl` contains challenge markers such as `__cf_chl_rt_tk`, login/auth/challenge fragments, or Cloudflare interstitial content.

### Pitfall 2: False `ready` From Early Worker Bootstrap
**What goes wrong:** Control surfaces show `ready` because the browser context launched, even when ChatGPT is challenged or logged out.
**Why it happens:** `browserContextReady` flips true before any ChatGPT usability proof, and pool health is derived from ports plus `/health`.
**How to avoid:** Add a usable-runtime state or evidence requirement before `ready` is allowed to gate rollout work.
**Warning signs:** Manual worker start behaves healthier than controller start, or `ready` workers still fail bootstrap immediately.

### Pitfall 3: Comparing Different Auth States
**What goes wrong:** Runtime A is tested on a warm logged-in profile while Runtime B is tested on a stale or challenged profile, making the comparison useless.
**Why it happens:** The system currently has multiple durable profiles and visible/manual steps.
**How to avoid:** For each comparison row, record worker, profile, manual-auth freshness, runtime class, and timestamp.
**Warning signs:** Results differ, but the phase cannot prove whether the profile or runtime changed.

### Pitfall 4: Picking Docker/Xvfb Without Explicit Headed Mode
**What goes wrong:** The team decides to test the Docker alternative but accidentally leaves it in the same hidden/headless semantics.
**Why it happens:** The existing Docker worker stack already has browser-access infrastructure, which makes it easy to assume it is headed by default.
**How to avoid:** Make runtime mode explicit in compose/env and prove that a real headed browser is running under Xvfb before evaluating ChatGPT behavior.
**Warning signs:** Browser viewer opens but there is no actual browser surface, or worker config still resolves to `hidden_runtime`.

### Pitfall 5: Letting Phase 10.2 Become An Endless Retry Loop
**What goes wrong:** The phase burns time on small flag changes, timing changes, or one-off selectors without producing a decision.
**Why it happens:** Browser automation failures often tempt teams into iterative tweaking.
**How to avoid:** Define the matrix and stop condition before implementation: one bounded rescue attempt for current hidden runtime, one concrete alternative proof, then a written decision.
**Warning signs:** New retries are proposed without new evidence fields or without moving the decision forward.

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Old Chrome headless was a separate browser implementation | Chrome headless and headful now share the main browser code; old headless lives on as `chrome-headless-shell` | Chrome 132-era docs | Headless/headful rendering differences are smaller than before, but this does not override challenge systems that still explicitly block headless and automation |

**Deprecated/outdated:**
- Old assumption: `new_chat_selector_not_found` is the main hidden-runtime problem. Current evidence shows it is downstream of challenge flow.
- Old assumption: a reachable browser context is close enough to `ready`. For rollout decisions, that is now too weak.

## Open Questions

1. **Is one bounded launch-transport re-test of current host hidden runtime still worth doing?**
   - What we know: Current hidden runtime fails on all three workers, and visible auth succeeds on at least one identical durable profile.
   - What's unclear: Whether one supported browser-channel launch change or better evidence instrumentation would change the result on a single worker.
   - Recommendation: Allow exactly one single-worker bounded re-test with trace/header artifacts. If it still challenges, stop.

2. **Can the Docker/Xvfb alternative clear ChatGPT bootstrap when run explicitly headed?**
   - What we know: The repo already has Xvfb/x11vnc/websockify infrastructure, and Playwright officially supports headed Linux via Xvfb.
   - What's unclear: Whether current ChatGPT/Cloudflare behavior will treat that environment as sufficiently usable for household flow.
   - Recommendation: Make this the primary alternative proof candidate in Phase 10.2.

3. **If Docker/Xvfb also fails, what is the next concrete path?**
   - What we know: Windows officially supports alternate desktops and `lpDesktop`-targeted process launch, so a non-visible native desktop/session path is possible.
   - What's unclear: Whether that can be built cheaply enough for v1.2 without creating a new runtime subsystem.
   - Recommendation: Do not build it in Phase 10.2. Record it as the next design phase only if the Docker/Xvfb proof fails.
