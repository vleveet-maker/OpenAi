# Phase 10.2 Plan 01: Summary

The control plane now distinguishes reachability from rollout usability instead of pretending a listening process is automatically safe to route.

## Accomplishments

- Host-controller start results now report `already_running`, `started`, or `startup_timeout` from observed startup behavior instead of returning only request acceptance.
- Control-api worker state now includes `runtimeCapability` with exact values `unreachable`, `reachable_but_unusable`, and `usable`.
- Worker health tracking now preserves `browserContextReady`, `lastRelayAt`, and `lastRelayFailureCode` so rollout truth is based on more than raw port liveness.
- Internal worker payloads now expose `runtimeCapability`, `browserContextReady`, `lastRelayAt`, and `lastRelayFailureCode` verbatim.
- Host-pool refresh now preserves controller worker rows and no longer collapses reachable controller data to an empty worker list in the tested paths.

## Key Decisions

- Separate control-plane truth into startup observation and runtime capability instead of a binary ready/disconnected model.
- Treat auth/challenge-style runtime failure as `reachable_but_unusable`, not as `ready`.
- Keep `usable` intentionally strict so later rollout smoke can rely on it rather than on mere browser process reachability.

## Verification

- `cmd /c npm.cmd test --prefix services/host-controller`
- `cmd /c npm.cmd test --prefix services/control-api`
- `cmd /c npm.cmd run build --prefix services/control-api`
- live `/internal/workers` check after `control-api` restart showed `runtimeCapability` on real worker payloads

## Residual Risk

- Live pool truth now depends on the corrected host-native override being the way the stack is started; bypassing that override would still silently remove host-controller wiring.
