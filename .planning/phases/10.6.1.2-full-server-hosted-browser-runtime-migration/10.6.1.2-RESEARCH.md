# Phase 10.6.1.2 Research

## Findings

### 1. Linux relay plus Windows runtime is already the proven split

The relay/API on Linux is not speculative anymore. The unstable piece was the attempt to move GUI browsers onto Linux. That means the correct next step is not another Linux browser experiment; it is packaging the current working Windows runtime as its own deployable block.

### 2. `host-controller` is already the right local control boundary

The current repo already has a useful Windows-native control plane:

- [server.mjs](d:/OpenAi/services/host-controller/src/server.mjs)
- [host-controller.mjs](d:/OpenAi/services/host-controller/src/host-controller.mjs)

That surface can:

- start one worker
- stop one worker
- start a pool
- stop a pool
- report truth about worker ports and runtime state

So the Windows Server deployment should reuse `host-controller`, not invent a second launcher.

### 3. Browser workers still need an interactive Windows session

The runtime depends on real GUI browser windows for manual login and reauth. That means:

- `host-controller` can autostart
- reverse tunnels can autostart
- but GUI browsers should live in an interactive logon session, not service-only Session 0

For deployment prep, scheduled tasks at user logon are a better baseline than trying to run the browsers as Windows services.

### 4. Reverse tunnels remain the honest remote contract

The current Linux relay already expects worker ports through reverse tunnels such as:

- `14021 -> 4021`
- `14022 -> 4022`
- `14023 -> 4023`
- `14024 -> 4024`
- `14025 -> 4025`
- `14026 -> 4026`
- `14027 -> 4027`

That means the current remote API can stay stable while the Windows block moves from this laptop onto a Windows Server host.

### 5. Direct worker proof is more truthful than the old local stack for this phase

The new direct verification path:

- [test-windows-browser-block-matrix.ps1](d:/OpenAi/infra/host-worker/test-windows-browser-block-matrix.ps1)

checks the Windows block through:

- `host-controller`
- direct `worker-agent` bootstrap
- direct `worker-agent` relay

That avoids false negatives from the local Docker/control-api stack when this phase is really about browser-runtime truth.
