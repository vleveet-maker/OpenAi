# Phase 10.1: Hidden runtime after manual login - Research

**Completed:** 2026-03-28
**Question answered:** What do we need to know to plan a safe visible-auth then hidden-runtime split for household host-native workers?

## Findings

### The Current Code Already Contains Half Of The Hidden Runtime

- `workers/agent/src/server.ts` already parses `WORKER_HEADLESS`, and `workers/agent/src/browser-launch.ts` already launches a persistent browser context itself when no CDP endpoint is supplied.
- The current host-native path still opens windows because `infra/host-worker/start-host-native-worker.ps1` always launches a real Edge or Chrome process first and always sets `WORKER_CDP_ENDPOINT_URL`, so the worker-agent attaches to an already visible browser over CDP.
- That means the missing piece is not a brand-new runtime stack. It is an explicit mode split in the host scripts and control plane.

### Playwright Favors A Sequential Split, Not Dual Use Of One Profile

- Playwright documents `browserType.launchPersistentContext(userDataDir, options)` as the API for a persistent context backed by one user data directory.
- The same docs explicitly note that browsers do not allow launching multiple instances with the same user data directory.
- For this phase, that means visible auth and hidden runtime must be sequential against the same durable profile. We should not try to keep a visible browser and a hidden browser alive at the same time on one worker profile.

### CDP Is Useful For Manual Visible Auth, But Not Ideal As The Steady-State Automation Path

- Playwright documents `chromium.connectOverCDP()` as a way to attach to an existing browser, but also says it is significantly lower fidelity than the normal Playwright protocol connection.
- That is a good fit for the manual visible-auth step, where the operator needs a real branded browser window and the agent only needs to observe or reuse that session later.
- For steady-state hidden runtime, the better shape is to let the worker-agent own the persistent browser context directly instead of always hanging off a CDP-connected desktop browser.

### Minimized Windows Are Not The Same As Hidden Runtime

- The current scripts use `WindowStyle Minimized`, which only changes how the browser appears on the desktop.
- Playwright's headed/headless guidance makes the distinction explicit: browsers run headless by default, and visible windows are the `headless: false` case.
- So Phase 10.1 should implement a true headless or otherwise non-visible runtime, not just a less-obvious visible window.

### Hidden Runtime Still Needs The Same Proxy Contract

- The current visible host-native flow routes browser traffic through the local mixed proxy by passing `--proxy-server=<mixed-proxy-url>` to the branded browser process.
- If the hidden runtime launches a persistent context directly from the worker-agent, it still needs the same proxy path or else we change network behavior without meaning to.
- The simplest implementation direction is to keep one `WORKER_PROXY_SERVER` contract and apply it to both visible and hidden launch modes.

### Reliability Policy Must Be Encoded Operationally, Not Just In Conversation

- The user decision for this phase is strict: if a worker loses ChatGPT auth after the deliberate visible-login then hidden-runtime split, that should be treated as evidence that the current multi-browser runtime is not robust enough.
- That does not mean Phase 10.1 must solve the architecture review itself. It does mean the runtime and internal operator surfaces should expose hidden-mode auth loss clearly and should never auto-open visible windows again behind the operator's back.

### Recommended Direction

- Add an explicit runtime mode contract with two exact modes: visible manual auth and hidden steady-state runtime.
- Keep visible mode CDP-based so the operator can log in through a real browser window when needed.
- Make hidden mode the default for pool start and routine relay by launching the persistent browser directly from the worker-agent with `WORKER_HEADLESS=true` and no CDP endpoint.
- Add explicit internal transitions for "start visible login" and "complete login -> hidden runtime".
- Treat hidden auth loss as `reauth_required` plus a clear reliability-review signal, not as a cue to auto-open windows or silently continue.

## Validation Architecture

- `workers/agent` should gain tests for runtime mode parsing, hidden launch without CDP, and proxy propagation into the hidden launch path.
- `services/host-controller` should gain tests proving `startPool()` requests hidden runtime and per-worker starts can request visible auth explicitly.
- `services/control-api` should gain tests for manual-auth start, manual-auth completion into hidden runtime, worker status payloads that expose runtime mode, and operator-facing copy that makes hidden auth failure explicit.
- Manual live verification remains required: one worker must be logged in visibly, promoted to hidden runtime, and then pass a relay smoke without any visible browser window remaining on the desktop.
