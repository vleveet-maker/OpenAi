# Phase 10.1 Plan 02: Summary

Control-api now treats visible manual auth and hidden steady-state runtime as explicit operator actions rather than implicit browser side effects.

## Accomplishments

- Propagated `runtimeMode`, `headless`, `cdpAttached`, and `proxyServerConfigured` through host-controller client types, worker registry state, worker health polling, and `/internal/workers` payloads.
- Added hidden-runtime auth-loss wording to worker status change events so the operator sees `architecture review required` instead of another silent restart loop.
- Added host-only `POST /internal/workers/:id/manual-auth/start` and `POST /internal/workers/:id/manual-auth/complete`.
- Wired those routes so visible auth is explicit, hidden runtime promotion is explicit, and Docker workers return `409` for the host-only transition flow.
- Updated the internal admin page with `Start visible login`, `Start visible reauth`, `Complete login -> hidden`, runtime-mode badges, and hidden-runtime-only pool copy.
- Added focused route and HTML tests for the new host-worker transition flow.

## Key Decisions

- Keep visible browser startup strictly behind explicit internal routes; no background path is allowed to reopen windows automatically.
- Surface hidden-runtime auth loss as a reliability signal in existing observability flows instead of inventing a separate public workflow.
- Reuse the same internal admin surface for both lifecycle control and explicit runtime-mode transitions so the operator has one source of truth.

## Verification

- `cmd /c npm.cmd test --prefix services/control-api`
- `cmd /c npm.cmd run build --prefix services/control-api`

## Residual Risk

- The new controls and telemetry are code-and-test verified, but the live visible-to-hidden transition still depends on an operator running the probe against a real logged-in worker profile.
