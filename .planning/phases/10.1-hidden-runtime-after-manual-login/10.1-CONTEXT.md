# Phase 10.1: Hidden runtime after manual login - Context

**Gathered:** 2026-03-28
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase converts the household host-native worker path into an explicit two-stage runtime:

1. a visible interactive browser is allowed only when the operator intentionally starts manual login or reauthentication for one worker
2. once that manual step is complete, routine household use must run through a hidden or headless runtime that does not open browser windows on the operator desktop

The phase covers the worker-agent launch contract, host-controller and PowerShell start paths, internal control-api routes, internal admin controls, and a verification path that proves the hidden runtime is actually being used.

This phase does not add new public product surface area, replace ChatGPT browser relay with an API, automate CAPTCHA bypass, or declare the current multi-browser architecture permanently solved. It only establishes the visible-auth then hidden-runtime contract and makes runtime instability visible instead of hand-wavy.

</domain>

<decisions>
## Implementation Decisions

### Visible Auth vs Hidden Runtime

- **D-01:** Visible interactive browser use is allowed only for first login or manual reauthentication.
- **D-02:** Routine household work must use a true hidden runtime, not merely a minimized or hidden desktop window.
- **D-03:** Pool start must default to hidden runtime for every host-native worker. Visible mode must be an explicit per-worker operator action.

### Transition Contract

- **D-04:** A worker profile may move from visible auth mode to hidden runtime only sequentially. The visible browser instance must stop before the hidden runtime starts against the same durable profile.
- **D-05:** The same durable worker profile should be reused across both modes. The phase is about runtime visibility, not about throwing away saved profile state.
- **D-06:** If the hidden runtime later reports `reauth_required` or `bootstrap_auth_required`, the system must not silently reopen a visible browser or pretend the worker is healthy.

### Reliability Review Rule

- **D-07:** Hidden-runtime auth loss after deliberate manual login is treated as architecture evidence, not just a nuisance. Operator-facing wording should make it clear that recurring failures mean the current multi-browser runtime may need replacement rather than more small patches.
- **D-08:** The phase should surface this as a clear runtime-reliability review signal, using existing internal observability patterns where possible, instead of inventing a new public workflow.

### Control-Plane Ownership

- **D-09:** control-api remains the operator-facing source of truth for host worker status, runtime mode, and manual-auth transitions.
- **D-10:** The internal admin page should show whether a host worker is in visible auth mode or hidden runtime and should offer explicit actions that mirror the real operator flow.
- **D-11:** The hidden-runtime validation path belongs in internal tools and maintainer docs, not in the public app.

### Explicit Non-Goals

- **D-12:** Do not attempt unattended login, CAPTCHA solving, or stealth/anti-detection tactics in this phase.
- **D-13:** Do not redesign the future mobile multi-chat app surface here.
- **D-14:** Do not declare the `dad` profile fixed by planning alone. Phase 10's remaining live tail still needs manual reauth and later proof.

### the agent's Discretion

- Exact internal route names and payload shapes for visible-auth start and hidden-runtime promotion
- Exact field names used to expose runtime mode, headless state, and reliability hints through internal health payloads
- Whether hidden-runtime verification extends the existing relay smoke script or adds a companion script, as long as the operator and maintainer path stays unambiguous

</decisions>

<specifics>
## Specific Ideas

- The current host-native path is only "less visible" because browsers launch minimized. It is not truly hidden.
- The worker-agent already parses `WORKER_HEADLESS`, and `launchWorkerBrowser()` already knows how to use `launchPersistentContext()` when no CDP endpoint is supplied.
- The hidden-runtime path should build on those existing pieces instead of inventing a second browser stack.
- The current host-native scripts pass proxy settings only to the visible external browser. Hidden runtime will need an equivalent proxy path so household traffic still goes through the same mixed proxy.
- The internal admin page should stop implying that host workers are only managed by `Start pool / Stop pool`; it now needs explicit per-worker manual-auth actions.

</specifics>

## Deferred Ideas

</deferred>
