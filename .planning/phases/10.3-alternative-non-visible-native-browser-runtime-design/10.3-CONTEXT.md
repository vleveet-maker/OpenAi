# Phase 10.3: Alternative non-visible native browser runtime design - Context

**Gathered:** 2026-03-28
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase exists because Phase 10.2 already finished the runtime review and rejected both currently available non-visible browser paths for rollout use:

1. current host `hidden_runtime`
2. current `docker_headed_xvfb` candidate

The next step is therefore not another generic retry. It is a design-and-implementation phase for one concrete replacement runtime class that preserves the user's operating policy:

- manual first login or reauthentication may stay visible
- routine household browsing must not show windows on the operator's main desktop
- the durable browser profile must remain the same across visible auth and steady-state use

The selected primary direction for this phase is:

- a same-session Windows alternate-desktop runtime for steady-state browser operation

That means:

- the browser remains native Edge/Chromium on Windows
- the browser does not rely on the rejected `headless=true` path
- the browser does not rely on the rejected Docker/Xvfb path
- the design should avoid introducing a second Windows user account or stored Windows credentials unless execution proves that same-session alternate desktop is impossible

This phase covers:

- defining the runtime contract for the replacement non-visible native runtime
- planning how host-controller, control-api, and worker-agent move from `visible_auth` into that runtime
- planning the bounded live proof that either selects the runtime or keeps Phase 11 blocked with evidence

This phase does not cover:

- the future mobile multi-chat product UX
- CAPTCHA bypass or stealth anti-detection stacks
- replacing browser relay with the OpenAI API
- broader milestone expansion beyond the runtime gate that blocks Phase 11

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** `visible_auth` and routine non-visible runtime are distinct runtime classes and must be treated as such.
- **D-02:** The current host `hidden_runtime` is rejected for rollout use.
- **D-03:** The current `docker_headed_xvfb` candidate is also rejected for rollout use.
- **D-04:** Phase 11 must remain blocked until this phase either selects a replacement runtime or records a fresh rejection with evidence.

### Runtime Policy

- **D-05:** Manual login or reauthentication may still happen in a visible interactive browser.
- **D-06:** Routine household usage must not place visible browser windows on the operator's main desktop.
- **D-07:** The replacement steady-state path must reuse the same durable profile that was just authenticated visibly.
- **D-08:** Prefer a same-session Windows desktop isolation approach before any solution that requires a second Windows user, stored Windows credentials, or a separate VM.

### Explicit Non-Goals

- **D-09:** Do not add stealth plugins, CAPTCHA bypass tooling, or anti-detection experiments in this phase.
- **D-10:** Do not move the product to direct OpenAI API usage in this phase.
- **D-11:** Do not ship the future mobile multi-chat and image-attachment UX here.

### the agent's Discretion

- Exact helper shape for Windows alternate-desktop launch, as long as it does not depend on a newly installed SDK
- Exact runtime metadata contract between launcher, host-controller, and worker-agent
- Exact proof artifact shape that decides whether the runtime is accepted for Phase 11

</decisions>

<specifics>
## Specific Ideas

- Official Windows desktop APIs make a same-session alternate desktop feasible: a process can be launched onto a named desktop via `STARTUPINFO.lpDesktop`, and the calling process does not need to create a second Windows user just to separate surfaces.
- `SwitchDesktop` is a visibility control, not a requirement. Routine runtime can stay on a non-default desktop without switching the operator's visible desktop.
- The host currently has PowerShell 5.1 and a .NET runtime host but no .NET SDK. That means execution should not assume a new compiled-toolchain install. A PowerShell-hosted Win32 interop helper or checked-in helper binary is acceptable; an SDK bootstrap as a first step is not preferred.
- The existing successful live path already uses a native Edge browser and CDP attach during `visible_auth`, so Phase 10.3 should reuse as much of that operational shape as possible instead of inventing a completely different browser-control protocol.
- Because Playwright documents `connectOverCDP()` as lower fidelity than a Playwright protocol connection, the replacement design should keep CDP scope narrow and evidence-backed rather than assuming it is automatically equivalent to a Playwright-managed runtime.

</specifics>
