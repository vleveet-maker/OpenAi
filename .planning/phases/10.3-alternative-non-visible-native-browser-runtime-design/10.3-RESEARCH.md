## Summary

The strongest next runtime candidate is a same-session Windows alternate-desktop browser runtime. Official Windows desktop documentation confirms three important pieces. First, `CreateDesktop` can create a separate desktop object within the current interactive window station. Second, `STARTUPINFO.lpDesktop` can target a named desktop when launching a new process. Third, desktop association is part of the process/thread connection rules, so a child process can be directed onto a specific desktop without creating a second Windows user session. That fits the project policy much better than the rejected headless path and better than introducing stored Windows credentials.

This means the project can keep the current product boundary intact:

- visible manual login remains on the operator's normal desktop
- the same durable Edge profile is reused afterward
- steady-state browser windows move to a named alternate desktop and stop appearing on the operator's main desktop

The most important tradeoff is transport. Playwright documents `connectOverCDP()` as lower fidelity than a Playwright protocol connection, which means the replacement runtime should not be treated as "done" just because the browser process launches. The phase must keep a proof step that confirms actual ChatGPT usability after the transition. Still, CDP is acceptable here because the project already has a live-success baseline for visible auth using the same Edge + CDP shape, and Windows alternate-desktop launch is easier to combine with a browser process that exposes CDP than with a Playwright-owned browser process.

The main alternative that looks plausible on paper but is not recommended is a second Windows user or credentialed launch path such as `CreateProcessWithLogonW`. Official docs and troubleshooting material show that these paths introduce credential handling and account-format edge cases that are unnecessary if the same-session desktop model works. Given the user's security preference and the current host toolchain, the right Phase 10.3 plan is:

1. build the same-session alternate-desktop runtime contract first
2. integrate it into host-controller and internal admin
3. end with a bounded live accept/reject decision that either unblocks Phase 11 or keeps it blocked

**Primary recommendation:** Plan Phase 10.3 around a Windows same-session alternate-desktop runtime with `host_alternate_desktop` as the new steady-state runtime class, explicit `visible_auth -> alternate_desktop` transitions, and a live runtime decision gate before Phase 11.

## Architecture Patterns

### Pattern 1: Same-Session Alternate Desktop For Steady-State Runtime
**What:** Launch the routine browser on a named desktop inside the current interactive window station instead of on the operator's visible `Default` desktop.

**When to use:** After manual login is complete and the worker returns to routine household usage.

**Why:** Windows docs explicitly support creating desktops and targeting them through `lpDesktop`, which gives a non-visible native runtime without moving to a second Windows identity.

**Example shape:**
```text
visible_auth (main desktop, same profile)
  -> stop browser cleanly
  -> create/open desktop "OWMCGPT\\worker-dad"
  -> launch Edge with --user-data-dir=<same profile> and --remote-debugging-port=<same port>
  -> attach worker-agent over CDP
```

### Pattern 2: Runtime Metadata Must Be First-Class
**What:** The launcher should write durable metadata for the alternate-desktop browser process.

**When to use:** Every time the browser enters the replacement steady-state runtime.

**Why:** Host-controller, stop scripts, and worker-agent all need the same truth about desktop name, browser PID, runtime class, and CDP port.

**Example:**
```json
{
  "workerId": "dad",
  "runtimeClass": "host_alternate_desktop",
  "runtimeMode": "alternate_desktop",
  "desktopName": "OWMCGPT\\worker-dad",
  "browserPid": 12345,
  "cdpPort": 9222,
  "profilePath": "D:\\OpenAi\\infra\\data\\host-profiles\\dad",
  "launchedAt": "2026-03-28T20:00:00+03:00"
}
```

### Pattern 3: Keep Visible Auth And Steady-State Runtime Separate
**What:** `visible_auth` remains a human workflow. `alternate_desktop` becomes the routine worker runtime.

**When to use:** In host-controller commands, internal routes, worker telemetry, and operator docs.

**Why:** The current project already proved that visible auth and non-visible use are not equivalent runtime classes.

### Pattern 4: Accept / Reject Gate Before Phase 11
**What:** Phase 10.3 should end in a binary decision artifact, not in "we have a new candidate and hope it works."

**When to use:** At phase completion and before Phase 11 resumes.

**Why:** Phase 10.2 already proved that rollout must not continue on runtime optimism.

## Common Pitfalls

### Pitfall 1: Treating Minimized Windows As Non-Visible
**What goes wrong:** The browser is merely minimized or hidden on the main desktop and can still pop or confuse the operator.
**How to avoid:** Use a separate desktop object and explicit runtime metadata so the browser is not just cosmetically hidden.

### Pitfall 2: Accidentally Reusing The Rejected `hidden_runtime`
**What goes wrong:** Control-api or host-controller transitions still map `Complete login` back to the old `hidden_runtime`.
**How to avoid:** Introduce a new explicit runtime mode name such as `alternate_desktop` and update operator copy and tests around it.

### Pitfall 3: Introducing Stored Credentials
**What goes wrong:** A launch path drifts toward `CreateProcessWithLogonW`, Task Scheduler credentials, or a second Windows user just to hide windows.
**How to avoid:** Make same-session alternate-desktop the default design and treat credentialed launches as a later fallback only if the primary design fails.

### Pitfall 4: Assuming CDP Reachability Means ChatGPT Usability
**What goes wrong:** The browser attaches successfully, but the runtime still fails on actual ChatGPT bootstrap or relay.
**How to avoid:** Keep the live proof contract from Phase 10.2 and require a real bootstrap or relay success before selecting the runtime.

### Pitfall 5: Requiring A New SDK During Execution
**What goes wrong:** The implementation plan assumes a C++ or .NET SDK that is not currently installed.
**How to avoid:** Prefer a PowerShell-hosted interop helper or checked-in helper binary; treat SDK installation as a last resort, not the opening move.

startup.cb = Marshal.SizeOf<STARTUPINFOW>();

CreateProcessW(

## Open Questions

1. **Will ChatGPT remain usable on an alternate desktop after visible login on the same profile?**
   - What we know: the normal visible desktop path works on live household profiles
   - What is unclear: whether moving the same browser identity to a non-default desktop changes Cloudflare/ChatGPT behavior materially
   - Recommendation: make this the primary live proof, not an assumption

2. **Should the launcher live entirely inside PowerShell or as a checked-in helper binary?**
   - What we know: no .NET SDK, C++, Rust, Go, or Zig toolchain is installed
   - What is unclear: whether PowerShell-hosted interop is sufficient and maintainable enough
   - Recommendation: start with a PowerShell-hosted helper contract in the plan and keep helper packaging as an implementation detail

3. **Do we need to preserve CDP ports per worker or allow dynamic assignment?**
   - What we know: the current operator flow and docs already assume fixed ports
   - What is unclear: whether alternate-desktop launch requires any port renegotiation
   - Recommendation: keep fixed worker CDP ports in Phase 10.3 to reduce change surface
