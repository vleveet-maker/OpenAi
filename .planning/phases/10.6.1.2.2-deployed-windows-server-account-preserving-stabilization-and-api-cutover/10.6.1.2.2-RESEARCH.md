# Phase 10.6.1.2.2 Research

## Findings

### 1. The deployed Windows Server is now the runtime source of truth

The repo can still change, but the server with nine live logged-in accounts is no longer a throwaway deployment target. That means the phase must start from:

- what is already deployed there
- what code or package version produced it
- what profiles and workers are already alive

### 2. Preserve-first work needs a freeze point before any uplift

Because the valuable asset is the live logged-in browser state, the first safe move is not "deploy latest". The first safe move is:

1. capture deployed version and startup truth
2. capture profile inventory and runtime topology
3. take a rollback-capable backup or cold snapshot

Only after that should code uplift begin.

### 3. Canary promotion is safer than full-pool restart

The current runtime boundary already has good worker-level control:

- `host-controller`
- per-worker launch scripts
- direct worker matrix probes

That means the safest rollout shape is:

1. single canary worker
2. three-worker subset
3. full nine-worker matrix

This is much safer than restarting all nine workers at once.

### 4. Public API cutover should be shadowed, not switched blindly

The new API path should first prove itself on:

- a shadow local port or shadow service path
- one known good canary worker
- a small validated worker subset

Only then should the edge be repointed.

### 5. Backup and rollback matter more than aggressive repair

If the server already contains valid accounts, the plan should prefer:

- cold copy or snapshot-backed backup when workers are stopped
- provenance capture for deployed code and settings
- rollback instructions that return to the frozen known-good state

This phase should explicitly avoid "just relogin everything" as a normal outcome.

## Planning Implications

- The phase must produce a deployment audit before touching code.
- The phase must add or formalize backup, rollback, and canary tooling.
- The phase must end with a nine-worker matrix and a cutover verdict, not just "service started".

## Recommended Execution Order

1. Freeze and audit the deployed Windows Server block.
2. Capture deployment provenance and backup/rollback assets.
3. Prepare canary-safe uplift and shadow API path.
4. Validate one worker, then a small subset, then all nine.
5. Only after that decide whether public API cutover is safe.
