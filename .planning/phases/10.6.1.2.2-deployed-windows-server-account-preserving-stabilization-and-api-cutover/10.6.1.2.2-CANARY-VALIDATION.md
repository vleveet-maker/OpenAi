## Short Report

The canary and subset paths are now explicit and evidence-backed.

What is proven:

- one worker can be started safely on the deployed Windows Server
- a small subset can be started safely on the deployed Windows Server
- a shadow public API can be started locally with an allowlisted single worker and complete a real `chat/completions` round-trip

- a full 9-worker API cutover

## Local Shadow API Proof

Purpose:

- prove the canary-safe shadow path works before anyone promotes a full Windows-side API cutover

Settings used:

- listen host: `127.0.0.1`
- listen port: `4012`
- allowlist: `shared-5`
- default worker: `shared-5`

Command path:

```powershell
powershell -ExecutionPolicy Bypass -File .\infra\windows-block\start-public-api.ps1 -ListenPort 4012 -SettingsPath infra\data\control-api\phase-10.6.1.2.2-test.local.json -SkipInstall -SkipBuild
powershell -ExecutionPolicy Bypass -File .\infra\windows-block\probe-public-api.ps1 -BaseUrl http://127.0.0.1:4012 -SettingsPath infra\data\control-api\phase-10.6.1.2.2-test.local.json -IncludeChatProbe -WorkerId shared-5 -EnsureWorkerStarted -StopWorkerWhenDone
```

Observed result:

- `GET /healthz` -> `200`
- `GET /v1/models` -> `200`
- `POST /v1/chat/completions` -> `200`
- `worker_id = shared-5`
- assistant reply: `probe-ok`

Important safety truth:

- only the allowlisted worker was started
- the probe stopped the canary worker again afterward
- the shadow API process on `4012` was stopped after proof

## Failure Classification

- direct `192.168.88.250:4010` is closed
- `http://192.168.88.250/...` redirects into a `Caddy` HTTPS path
