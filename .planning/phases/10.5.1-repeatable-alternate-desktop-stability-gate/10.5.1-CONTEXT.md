# Phase 10.5.1: Repeatable alternate desktop stability gate - Context

**Gathered:** 2026-03-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 10.5 proved one important thing and one uncomfortable thing:

1. `wife` can pass one full alternate-desktop proof (`Temporary Chat -> GPT-5.4 Thinking -> smoke-ok`)
2. that success is not yet repeatable

The latest live revalidation regressed the pool back to:

- `dad -> bootstrap_auth_required @ auth_check`
- `wife -> bootstrap_navigation_failed @ navigation`
- `shared-1 -> bootstrap_navigation_failed @ navigation`

Phase 10.5.1 is therefore not another selector cleanup phase and not rollout smoke itself. It is a stability gate phase whose only purpose is to answer this question honestly:

> can at least one named alternate-desktop worker pass the same non-visible validation more than once, in a way that is deterministic enough to trust before Phase 11?

This phase covers:

1. removing assignment-timeout noise from worker-specific validation
2. defining and surfacing a repeatability gate instead of treating one-off success as enough
3. running bounded repeated proof and ending with an explicit unblock-or-stay-blocked decision for Phase 11

This phase does not cover:

- a new browser runtime search
- public product expansion
- full-pool parity across all three workers
- Phase 11 rollout smoke itself

</domain>

<decisions>
## Implementation Decisions

### Locked Findings

- **D-01:** A one-off passing worker is no longer enough to reopen rollout smoke.
- **D-02:** `wife` remains the primary repeatability target because it already produced the only proof-backed success.
- **D-03:** `dad` remains an auth-renewal tail, not the first repeatability target.
- **D-04:** `shared-1` remains a confirmation target after the repeatability path is clean on `wife`.
- **D-05:** Assignment-timeout noise must be removed from the proof path before we judge runtime stability again.

### Gate Policy

- **D-06:** For `v1.2`, repeatability means two consecutive successful non-visible validation passes with a real relay success.
- **D-07:** The repeatability counter resets on any auth, bootstrap, relay, or worker-assignment failure.
- **D-08:** Phase 11 can only resume from a written decision that names a worker which crossed that repeatability gate.
- **D-09:** A worker may be "usable" from a single pass but still not yet "repeatably stable".

### Operator/Control-Plane Policy

- **D-10:** Validation must target one named worker deterministically, not by hoping global session routing picks the right worker.
- **D-11:** Operator/admin surfaces must show whether a worker is provisional or stable.
- **D-12:** The repeatability gate should live in product/control-plane truth, not only in maintainer scripts or memory.

### Explicit Non-Goals

- **D-13:** Do not invent a new runtime in this phase.
- **D-14:** Do not silently downgrade the gate back to "one pass is enough".
- **D-15:** Do not hide instability behind optimistic `ready` language.

### the agent's Discretion

- Exact shape of the worker-pinned validation path
- Exact names for repeatability-state fields exposed through worker truth and admin UI
- Exact proof order after `wife`, including whether `shared-1` is rerun in the same phase

</decisions>

<specifics>
## Specific Ideas

- The strongest sign of false confidence was not that `wife` passed once; it was that the very next fresh revalidation failed again.
- A worker-specific proof should not need to stop the whole pool or race the household scheduler if the product is ever going to feel routine.
- The milestone needs one more distinction in operator truth: `provisional` vs `repeatably stable`.
- If `wife` cannot pass twice in a row under a deterministic validation path, Phase 11 should stay blocked even if one historical success exists.

</specifics>
