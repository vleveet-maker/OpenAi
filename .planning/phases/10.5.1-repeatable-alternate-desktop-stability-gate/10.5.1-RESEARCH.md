## Summary

Phase 10.5 solved the wrong question well. It answered "can a worker ever pass?" with "yes, `wife` passed once." But the next live revalidation answered the more important question with "not yet": the result did not repeat.

The current proof stack has two separate weaknesses:

1. **runtime instability**
   - `dad` still reports `bootstrap_auth_required`
   - `wife` and `shared-1` fall back into `bootstrap_navigation_failed`
2. **proof-path instability**
   - the canonical probe still routes through timed sessions and can produce `assignment_timeout` or cross-worker assignment noise

That means Phase 10.5.1 should not just rerun the old proof more times. It should first make the proof deterministic for a named worker, then promote "repeatability" to a first-class operator truth.

The cleanest shape is:

1. add a worker-pinned validation path so proof does not depend on pool luck
2. define a small repeatability gate in control-plane truth
3. only then run repeated proof and write the final unblock decision

The repo already has almost all ingredients:

- `validate-runtime` exists end-to-end
- `test-host-worker-relay.ps1` already isolates non-target workers, so we know where assignment noise enters
- `worker-registry` and `internal-workers` already surface runtime truth fields, so adding a small repeatability state is a natural extension

The best bounded threshold for `v1.2` is **two consecutive passes**, not three:

- one pass is already proven insufficient
- two consecutive passes are enough to distinguish "one lucky run" from "repeatable enough to begin rollout smoke"
- requiring three passes would add time and operator friction before we even reach Phase 11, where broader smoke confidence already belongs

**Primary recommendation:** plan Phase 10.5.1 as three waves:
1. make validation deterministic for one named worker
2. make repeatability visible and stateful in the control plane
3. run bounded repeated proof and record the unblock-or-stay-blocked decision

## Architecture Patterns

### Pattern 1: Proof Must Stop Competing With The Household Scheduler
**What:** add a worker-pinned validation session path or equivalent deterministic worker-directed proof path.

**When to use:** any time the operator or host-controller validates one named worker.

**Why:** `assignment_timeout` is proof noise, not runtime truth.

**Recommended shape:**
```text
POST /internal/workers/:id/validation-session
  -> create a short-lived internal-only session pinned to that worker
  -> bootstrap + relay use the existing app/session stack
  -> session is cleaned up after proof
```

### Pattern 2: Repeatability Must Be State, Not Memory
**What:** store a small repeatability gate alongside worker truth.

**When to use:** after each non-visible validation run.

**Why:** a maintainer remembering that `wife` passed once is not enough for product truth.

**Recommended fields:**
```text
stabilityGateStatus: unstable | provisional | stable
stabilityPassCount: number
stabilityTargetPasses: 2
lastValidationAt: iso timestamp
lastValidationResult: pass | fail
```

### Pattern 3: Failure Must Reset The Gate
**What:** any auth, bootstrap, relay, or worker-assignment failure resets the repeatability counter.

**When to use:** every validation result update.

**Why:** otherwise the gate becomes a cumulative history badge instead of a real stability signal.

### Pattern 4: Phase 11 Must Unblock From Repeated Proof, Not Historical Proof
**What:** the final decision artifact should only unblock if one named worker reaches the gate.

**When to use:** at the end of the bounded repeated-proof sequence.

**Why:** the current issue is not absence of proof; it is lack of repeatable proof.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| worker-specific validation | "stop other workers and hope the scheduler cooperates" | pinned validation session or equivalent deterministic worker path | removes assignment-timeout false negatives |
| repeatability tracking | notes in docs only | explicit worker truth fields and admin rendering | keeps operator state honest |
| Phase 11 unblock | "wife passed once before" | repeated proof artifact from this phase | matches the actual risk |

## Common Pitfalls

### Pitfall 1: Mistaking Scheduler Noise For Runtime Failure
**What goes wrong:** `assignment_timeout` gets treated as if ChatGPT bootstrap is the real problem.
**How to avoid:** target the worker directly for proof before judging runtime stability.

### Pitfall 2: Counting Historical Success As Repeatability
**What goes wrong:** one old pass keeps the milestone optimistic even after the latest run failed.
**How to avoid:** define a consecutive-pass gate with reset-on-failure semantics.

### Pitfall 3: Overfitting Repeatability To `wife` Without Recording That Fact
**What goes wrong:** the project silently assumes `wife` is special but never states it.
**How to avoid:** explicitly name `wife` as the first target and carry `dad/shared-1` as debt until they catch up.

## Open Questions

1. **Should the deterministic validation path create a real session or talk directly to the worker?**
   - Recommendation: create a short-lived internal session pinned to the worker so the proof still exercises the real session/bootstrap/relay stack used by the product.

2. **Should two passes happen back-to-back or be separated by a runtime restart?**
   - Recommendation: require the second pass after a controlled alternate-desktop restart of the same worker. That is a stronger repeatability signal without expanding into full rollout smoke.

3. **Should `shared-1` also need to pass in this phase?**
   - Recommendation: no. `wife` is enough to unblock Phase 11 again, as long as the proof is repeatable this time.
