# Phase 10.5.1 Plan 02: Summary

One successful validation is no longer treated as rollout-ready by default.

## Accomplishments

- Added repeatability gate fields to worker truth:
  - `stabilityGateStatus`
  - `stabilityPassCount`
  - `stabilityTargetPasses`
  - `lastValidationAt`
  - `lastValidationResult`
- Updated `POST /internal/workers/:id/validate-runtime` so:
  - a passing proof increments the counter
  - `1/2` becomes `provisional`
  - `2/2` becomes `stable`
  - any auth/bootstrap/relay/routing failure resets the gate back to `unstable`
- Surfaced the new fields through `/internal/workers` and `/internal/workers/:id/status`.
- Rendered the gate in internal admin with explicit operator language such as `Repeatability: provisional (1/2)` and `Repeatability: stable (2/2)`.

## Key Decisions

- Runtime capability and repeatability are different truths:
  - `runtimeCapability=usable` can describe one pass
  - `stabilityGateStatus=stable` only happens after repeated proof
- The milestone should unblock from gate state, not from historical memory of one lucky run.

## Verification

- `cmd /c npm.cmd test --prefix services/control-api`
- `cmd /c npm.cmd run build --prefix services/control-api`

## Residual Risk

- The gate can now describe stability honestly, but it does not create stability by itself. A worker still has to survive repeated live validation.
